## 2. Binding conditions: artifact and a proof that fails on a violation
Each is an acceptance criterion; a Gate 2 file that does not satisfy it is rejected.

**C1 (table lock before batch locks in initialization).** Artifact: A-07 and A-07-TEST. Order inside the initialization transaction: (1) lock the membership table and disable the stamping trigger in one statement sequence, (2) only then take batch row locks in ascending id order, (3) initialize NULL negative rows only, (4) re-enable the trigger, commit. Proof (A-07-TEST, three real sessions with an explicit barrier sequence): (1) session S1, a membership writer, updates a membership row to a negative status and does **not** commit (it now holds a row-exclusive lock on the membership table and, through the stamping trigger, the batch row lock); (2) session S2 starts the initializer, which must block on the membership-table lock; session S3 (observer) confirms by `pg_stat_activity` and `pg_locks` that S2 is waiting on the table lock and **holds no batch row lock**; (3) S1 commits, S2 acquires the table lock, then the batch locks, and completes with no deadlock error; (4) the test asserts the trigger is **enabled** after the successful run and after a second run with a forced error in the middle (catalog read of `pg_trigger.tgenabled`), and zero negative rows have a NULL stamp afterwards. A control run in the former order (batch lock first) is run only in a disposable test schema to show it deadlocks, so the test would fail the wrong order. The SQL review rejects any file that takes a batch row lock before the table lock.

**C2 (exact `grp_batch_writer` boundary).** Artifact: A-01 (role, grants, manifest, assertions) and A-01-TEST. The file contains:
1. **The trusted migration identity**, stated as the value measured by FU4-J1 (`session_user` and `current_user` of the SQL Editor run, expected `postgres`) and asserted at the top: the file fails if `current_user` is not that role.
2. **Role attributes:** `NOLOGIN`, not superuser, no BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION; **the exact post-A-01 edge set** in `pg_auth_members` is defined once: exactly **one** row whose granted role is `grp_batch_writer`, with member = the trusted identity, `set_option` true, `inherit_option` false, `admin_option` false; and **no** row whose member is `grp_batch_writer` (it is a member of nothing). A-01 makes this true by creating the role, then issuing the one `GRANT ... WITH SET TRUE, INHERIT FALSE, ADMIN FALSE` and revoking any other grant on the role that the server may have recorded at creation (no assumption is made about such a grant; FU4-J1 runs before the role exists and cannot show it). The test compares `pg_auth_members` to this set **exactly** (extra or missing rows fail). Superuser reachability is **not an edge**: it is a role attribute, handled by item 3.
3. **A recursive assertion that does not trust any edge list:** for every role other than the trusted identity and superusers, `pg_has_role(role, 'grp_batch_writer', 'MEMBER')`, `'USAGE'` and `'SET'` are all false; and the set of roles that are superuser or CREATEROLE (the only roles that can reach or grant the role without an edge) equals the set recorded in FU4-J1 (a new such role fails the test). Because it uses the server's own closure, an unnamed intermediate role cannot hide a path.
4. **An exact approved-writer manifest** (a `VALUES` list of function name plus identity arguments, so overloads are distinguished) covering every function the brief lists, including the invite functions, the stamping trigger function and the allocator. Assertion A: the set of routines owned by `grp_batch_writer` equals the manifest exactly (an extra owned routine fails; a missing one fails). Assertion B: **a reviewed-closure manifest**: every routine in a freshly computed closure (same definition as FU4-J2b, across **every non-system schema** with schema-qualified identities; once the invite relation exists the seed also includes its name: mentions the group tables, the invite relation, `invite_token`, a view over them, dynamic SQL, or calls such a routine) must appear either in the writer manifest or in a second list, the **reviewed non-writer manifest** (each entry reviewed against its saved definition from FU4-J2c, with the reason it is not a writer); a routine in the closure that is in neither list fails the test. This is the detector for an omitted writer: a new or unlisted routine capable of a protected write cannot pass.
5. **Behavioural proof of the guard** (A-02-TEST): a `SECURITY DEFINER` probe routine owned by the trusted identity (not the writer) that tries to change `order_seq`, a batch marker and a batch-shaped token is refused by the guard; the approved writers succeed.
6. **Exact privileges of the writer role:** only the table and sequence privileges the approved writers need, listed in the file and compared to `information_schema.role_table_grants` and `role_routine_grants`; the role owns no table.
Residual blind spot, stated: static inspection cannot prove the absence of a string-assembled write that does not use `EXECUTE`; closing it is the job of the guard (runtime refusal), the exact manifests above, and the adversarial real-role tests together.

**C3 (collision-safe allocation for every replacement token, atomic across both token domains).** Two token domains exist: the **invite relation** (invite tokens) and `study_groups.invite_token` (batch and non-batch groups). A token must never be equal in both. FU2-index records that `study_groups.invite_token` has **no unique index**. A check-then-insert inside an allocator is not enough: a non-batch group insert that takes the column default (`gen_random_uuid()`), or a client insert, does not call the allocator and could commit the same value between the check and the caller's commit. v3 therefore makes the guarantee **structural**, in four parts, all created in A-03:
1. **One shared transaction-level advisory lock key** for the token domain (`pg_advisory_xact_lock`), held until commit by every producer of a token.
2. **Token-domain guard triggers on both relations**, so that **every** producer is covered, whichever function or client statement writes it: a `BEFORE INSERT OR UPDATE OF invite_token` trigger on `study_groups` and a `BEFORE INSERT` trigger on the invite relation (token immutable afterwards). Each takes the shared lock first, then checks that the new value equals no invite token and no `study_groups.invite_token` (other than the row itself), and raises `token_collision` if it does (fail closed, nothing is written). Both are `SECURITY DEFINER` because the invite relation has no client privileges, with a pinned `search_path`; they are on the **reviewed non-writer manifest** (they read the tables, they change nothing). Because both producers take the same lock before checking and keep it until commit, two concurrent producers are serialized and the later one sees the earlier one's committed value; the check-then-commit gap is closed for default-generated, allocator-generated and rollback tokens alike.
3. **The allocator** `t001_alloc_token(candidates uuid[] DEFAULT NULL)`, owned by `grp_batch_writer`, `EXECUTE` revoked from `PUBLIC`, `anon`, `authenticated` and service roles: takes the shared lock, tries up to 10 candidates (supplied or `gen_random_uuid()`), rejects a candidate that equals any token in either domain, and raises `token_allocation_exhausted` when none is acceptable. It is a convenience that retries before the triggers would raise; **the guarantee is the triggers**.
4. **Call sites of the allocator (complete):** (1) A-06 `create_batch_group`: the invite token and, after step 5, the column token; (2) A-05 `create_batch_invite`; (3) A-09: every overwritten column token; (4) A-13: the minted non-expiring replacement token. A-07 copies the existing token (no allocation); its verification is the exact-mapping check. Non-batch group creation keeps the column default, **covered by the trigger of part 2**, not by the allocator.
**Status of this mechanism: PROPOSAL for the Gate 2 review of A-03.** It implements the approved brief's rule ("generated again if it equals any invite token or any other `invite_token`, fail closed") without changing any approved behaviour; QA is asked to confirm that, and the exact SQL hash is approved or rejected at Gate 2. A unique index on `study_groups.invite_token` (group-to-group uniqueness only) is a separate PROPOSAL in the same review.
**Tests (all deterministic).** (a) Sequential, through the candidate seam (optional argument, production value always NULL): a list whose first item equals an existing invite token, the second another batch group's column token, the third a non-batch group's column token, the fourth fresh returns the fourth after three rejections; only colliding values raise `token_allocation_exhausted`; the same two cases through A-09 and A-13. (b) **Concurrent, two real sessions with a barrier:** session S1 inserts a non-batch group whose default token is forced to value T (test-only forcing by inserting the group with an explicit token T) and does not commit; session S2 inserts an invite with token T (and, in the mirror run, S2 is the allocator with candidate T): S2 **blocks on the shared lock** (observed in `pg_stat_activity`/`pg_locks`), then after S1 commits S2 raises `token_collision` (or the allocator retries and returns a different value); the mirror run starts from an uncommitted invite token T and a group insert with T. (c) A direct client insert of a group whose explicit token equals an invite token is refused. (d) Catalog tests: the allocator's `EXECUTE` list; both guard triggers exist, are enabled and run before the data is written; a source test that every writer of a token in A-05, A-06, A-09 and A-13 either calls the allocator or is covered by the triggers (no producer escapes both).

**C4 (stamping trigger and initialization).** Artifacts: A-03 (trigger) and A-07 (initialization). A-03-TEST and A-07-TEST name each case explicitly: the **stale-stamp example** (original invite 1, invites 2 and 3, a deployment-window archive stamped 4: after a rerun the value is still 4 and invite 3 is older, so reuse gives `requested`); the rerun over a non-NULL row (unchanged); a **forged non-NULL `last_inactive_seq`** on a negative and on a non-negative INSERT and UPDATE (overwritten or nulled); unrelated UPDATEs through a direct client path and through a `SECURITY DEFINER` path (cannot change the value); a non-batch group (trigger no-op); and the **controlled old-writer harness** (a function that closes rows as the old `archive_batch_group` did, without taking the counter) producing a fresh stamp.

## 7. Standards for every file (from project memory and CLAUDE.md)
- SQL is a file under `docs/database/t001/`, never pasted into chat as the deliverable; every query has a `[FOLDER]` name and description.
- The Supabase SQL Editor wraps one run in **one transaction**: never mix persistent DDL with a verification `ROLLBACK`; `search_path` is set unquoted (`TO public, extensions`); search-path tests exercise a real write. TEST files are read-and-roll-back by design and contain no persistent DDL.
- Absence of a constraint, trigger, policy or grant is catalog-verified, never inferred from code; every fact a file relies on cites a saved evidence file.
- Real-role tests run as `anon` and `authenticated` (student, professor, group admin, platform admin, super admin) where relevant, not as the migration owner.
- Each file states its lock order (invite row, batch row, membership rows in ascending id, events insert; table lock before batch locks in initialization, C1) and is checked statement by statement.
- Client behaviour that needs a frontend change is listed in section 8 and is not deployed before its SQL.
