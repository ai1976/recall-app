## 2. Binding conditions: artifact and a proof that fails on a violation
Each is an acceptance criterion; a Gate 2 file that does not satisfy it is rejected.

**C1 (table lock before batch locks in initialization).** Artifact: A-07 and A-07-TEST. Order inside the initialization transaction: (1) lock the membership table and disable the stamping trigger in one statement sequence, (2) only then take batch row locks in ascending id order, (3) initialize NULL negative rows only, (4) re-enable the trigger, commit. Proof (A-07-TEST, two real sessions): session W holds a membership-table lock and a membership writer waits for a batch lock, the initializer is started in the former deadlock order (it must attempt the table/trigger lock while holding no batch row); the test asserts the initializer completes (no deadlock error), the trigger is **enabled** after both a successful run and a forced rollback in the middle (catalog read of `pg_trigger.tgenabled`), and zero negative rows have a NULL stamp afterwards. The SQL review rejects any file that takes a batch row lock before the table lock.

**C2 (exact `grp_batch_writer` boundary).** Artifact: A-01 (role, grants, manifest, assertions) and A-01-TEST. The file contains:
1. **The trusted migration identity**, stated as the value measured by FU4-J1 (`session_user` and `current_user` of the SQL Editor run, expected `postgres`) and asserted at the top: the file fails if `current_user` is not that role.
2. **Role attributes:** `NOLOGIN`, not superuser, no BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION; the single membership edge `grp_batch_writer` granted to the trusted identity `WITH SET TRUE, INHERIT FALSE, ADMIN FALSE` (so `SET LOCAL ROLE grp_batch_writer` works for steps 3, 5, 6 and ordinary statements of the identity do not inherit it).
3. **A recursive assertion that does not trust any edge list:** for every role other than the trusted identity and superusers, `pg_has_role(role, 'grp_batch_writer', 'MEMBER')`, `'USAGE'` and `'SET'` are all false; no edge with `admin_option` has `grp_batch_writer` as the granted role except the creator's implicit one recorded in FU4-J1 evidence; and the set of roles that are superuser or CREATEROLE equals the set recorded in FU4-J1 (a new such role fails the test). Because it uses the server's own closure, an unnamed intermediate role cannot hide a path.
4. **An exact approved-writer manifest** (a `VALUES` list of function name plus identity arguments, so overloads are distinguished) covering every function the brief lists, including the invite functions, the stamping trigger function and the allocator. Assertion A: the set of routines owned by `grp_batch_writer` equals the manifest exactly (an extra owned routine fails; a missing one fails). Assertion B: **a reviewed-closure manifest**: every routine in a freshly computed closure (same definition as FU4-J2b: mentions the group tables, the invite relation, `invite_token`, a view over them, dynamic SQL, or calls such a routine) must appear either in the writer manifest or in a second list, the **reviewed non-writer manifest** (each entry reviewed against its saved definition from FU4-J2c, with the reason it is not a writer); a routine in the closure that is in neither list fails the test. This is the detector for an omitted writer: a new or unlisted routine capable of a protected write cannot pass.
5. **Behavioural proof of the guard** (A-02-TEST): a `SECURITY DEFINER` probe routine owned by the trusted identity (not the writer) that tries to change `order_seq`, a batch marker and a batch-shaped token is refused by the guard; the approved writers succeed.
6. **Exact privileges of the writer role:** only the table and sequence privileges the approved writers need, listed in the file and compared to `information_schema.role_table_grants` and `role_routine_grants`; the role owns no table.
Residual blind spot, stated: static inspection cannot prove the absence of a string-assembled write that does not use `EXECUTE`; closing it is the job of the guard (runtime refusal), the exact manifests above, and the adversarial real-role tests together.

**C3 (collision-safe allocation for every replacement token).** One allocator, `t001_alloc_token(candidates uuid[] DEFAULT NULL)`, created in A-03, owned by `grp_batch_writer`, `EXECUTE` revoked from `PUBLIC`, `anon`, `authenticated` and service roles and granted to the writer role only. Behaviour: serialized by `pg_advisory_xact_lock`; up to 10 attempts; each attempt takes the next supplied candidate or `gen_random_uuid()`; a candidate is **rejected if it equals any invite token or any `study_groups.invite_token` (batch or non-batch)**; when the attempts are exhausted it raises `token_allocation_exhausted` (fail closed, nothing is written). FU2-index records that `study_groups.invite_token` has **no unique index**, so uniqueness is guaranteed by the allocator plus the verification queries, and **a unique index on the column is a PROPOSAL for the Gate 2 review of A-03**, not part of the approved brief. **Call sites (complete list):** (1) A-06 `create_batch_group`: the invite token and, after step 5, the column token; (2) A-05 `create_batch_invite`: new invite token; (3) A-09: every overwritten column token; (4) A-13: the minted non-expiring replacement token. A-07 does **not** allocate: it copies the existing column token into the original invite and its verification is the exact-mapping check. Non-batch group creation keeps the column default (not a replacement). **Test seam:** the optional `candidates` argument is the controlled seam; production callers always pass NULL. A-03-TEST calls the allocator with a candidate list whose first item equals an existing **invite token**, second equals another **batch group's column token**, third equals a **non-batch group's column token**, fourth is fresh: it returns the fourth and the test asserts three rejections; a list of only colliding values raises `token_allocation_exhausted`. A-09-TEST and A-13-TEST run the same retry and exhaustion cases through their own statements. A source test asserts that the four call sites call the allocator and none assigns a token from `gen_random_uuid()` directly, and a catalog test asserts the allocator's `EXECUTE` list.

**C4 (stamping trigger and initialization).** Artifacts: A-03 (trigger) and A-07 (initialization). A-03-TEST and A-07-TEST name each case explicitly: the **stale-stamp example** (original invite 1, invites 2 and 3, a deployment-window archive stamped 4: after a rerun the value is still 4 and invite 3 is older, so reuse gives `requested`); the rerun over a non-NULL row (unchanged); a **forged non-NULL `last_inactive_seq`** on a negative and on a non-negative INSERT and UPDATE (overwritten or nulled); unrelated UPDATEs through a direct client path and through a `SECURITY DEFINER` path (cannot change the value); a non-batch group (trigger no-op); and the **controlled old-writer harness** (a function that closes rows as the old `archive_batch_group` did, without taking the counter) producing a fresh stamp.

## 7. Standards for every file (from project memory and CLAUDE.md)
- SQL is a file under `docs/database/t001/`, never pasted into chat as the deliverable; every query has a `[FOLDER]` name and description.
- The Supabase SQL Editor wraps one run in **one transaction**: never mix persistent DDL with a verification `ROLLBACK`; `search_path` is set unquoted (`TO public, extensions`); search-path tests exercise a real write. TEST files are read-and-roll-back by design and contain no persistent DDL.
- Absence of a constraint, trigger, policy or grant is catalog-verified, never inferred from code; every fact a file relies on cites a saved evidence file.
- Real-role tests run as `anon` and `authenticated` (student, professor, group admin, platform admin, super admin) where relevant, not as the migration owner.
- Each file states its lock order (invite row, batch row, membership rows in ascending id, events insert; table lock before batch locks in initialization, C1) and is checked statement by statement.
- Client behaviour that needs a frontend change is listed in section 8 and is not deployed before its SQL.
