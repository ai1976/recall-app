If the ledger insert fails, the DELETE fails (fail closed; an account deletion would be refused until fixed, which is deliberate). **Token encoding (fixed here, not at Gate 2):** `owner_token = encode(sha256(convert_to(user_id::text, 'UTF8') || '\x00'::bytea || salt), 'hex')`, where `user_id::text` is the canonical lowercase hyphenated uuid text and `salt` is 32 random bytes (`gen_random_bytes(32)`); the cutover recomputes the identical expression for every `auth.users.id`. **Salt lifecycle:** one row in an owner-only table with a singleton constraint, created in B-04a, never updated or deleted by a trigger-enforced rule (a changed salt would orphan every token), never exported, never written to a repository or evidence file; it outlives the cutover and the observation, and its destruction afterwards is a Founder privacy decision. The salt is generated once, never exported and never written to the repository or to evidence files; it must outlive the cutover and the observation, and deleting it afterwards is a Founder privacy decision. Neither trigger rejects any write the F0 frontend makes (clients hold no DELETE or TRUNCATE, RUN 3). **Limits stated:** a superuser can disable a trigger or set `session_replication_role = replica`; a deletion made that way has no ledger row and SA (5.2) fails, which stops the cutover. Provenance does not depend on any marker that a routine can imitate (DEC-4 condition 1). TEST (rollback-only, including FAILURE INJECTION): an owner delete and a delete through the real cascade path each produce exactly one ledger row with the expected `owner_token` (and the forensic fields recorded); deleting one session of a live account produces a ledger row that SA rejects; a ledger failure aborts the delete; TRUNCATE is refused; the ledger and the salt are unreadable and unwritable by every client role. Failure injection: (1) the ledger insert is made to fail (revoked insert privilege on the ledger inside the transaction) and the DELETE aborts; (2) the salt row is missing and the DELETE aborts; (3) the cascade foreign key is dropped and recreated inside the transaction and the cutover assertion reports a different OID or definition hash; (4) a same-named routine in another schema, and a nested trigger call, each delete one session of a LIVE owner and SA rejects the removal because the owner is present; (5) a real owner deletion produces one ledger row per session whose token matches no live `auth.users` row; (6) `session_replication_role = replica` produces no ledger row and SA fails.

### 5.2 B-04b, enforcement (DEC-1, DEC-3, DEC-4 if approved)
- **Rule and mechanism:** a `source = 'manual'` row requires a non-NULL classification, as the approved plain CHECK `CHECK (source IS DISTINCT FROM 'manual' OR classification IS NOT NULL) NOT VALID` (brief B 4.2, B-I5). The expression is two-valued; D2 reports whether `source` can be NULL and the TEST attempts such an insert.
- **Precondition, with separate outcomes.** D3 and D4 classify every **discovered** path that can UPDATE, DELETE or TRUNCATE `study_sessions`: application code, edge functions, routines, trigger functions, rules and views, scheduled jobs, foreign-key referential actions, and any approved operational procedure (the single data fix below is one and ends before B-04b). The plain CHECK is used only if **no such path exists and no lead that could perform any of the three is unresolved**, subject to the DEC-4 treatment of account deletion below.
- **Role universe and effective capability (P4, P7).** Capability is judged on **effective** privilege (D2 v3 P4: `has_table_privilege` and `has_column_privilege`, which follow membership and inheritance, with `PUBLIC` read from the ACL, never passed to those functions), never on ACL rows and never on a role attribute. **`BYPASSRLS` is reported as a row-level-security fact only: it grants no privilege by itself.** The universe is `PUBLIC`, `anon`, `authenticated`, `service_role`, `authenticator`, and every non-system role that is a member of one of them or that D2 shows holding UPDATE, DELETE or TRUNCATE on `study_sessions`. **Required:** zero effective UPDATE, DELETE and TRUNCATE (table-level and column-level) for `PUBLIC`, `anon`, `authenticated` and every role inheriting from them, **and for `service_role`**. **Operation-specific rule for `service_role`:** INSERT and SELECT may be retained if D4 names an edge function that needs them; an edge function that needs UPDATE, DELETE or TRUNCATE on `study_sessions` is **not** a retention reason, it produces the corresponding stop outcome below (the DEC-4 account-deletion exception aside). **Accepted, reported residual (capability by ownership or superuser, not removable by an ACL change):** the table owner and superusers, and the operational principals and known runbooks that can use them: the Supabase SQL Editor role, the CLI login role and the single data fix of this plan. **What stops the cutover:** any client-facing role with effective capability; any scheduled job, routine or trigger that D3 shows performing one of the three operations through such a principal; any unresolved lead. The residual list is written into the Gate 3 request. **The zero-capability assertion is exactly the conjunction of three parts (D2 v3 output):** (a) every real role outside the allowlisted owner/superuser residual has `false` for every effective table-level and column-level UPDATE, DELETE and TRUNCATE row; (b) the ACL-derived PUBLIC section (grantee 0) lists none of those privileges, table-level or column-level; (c) no non-system role holds a sequence privilege beyond what the plan allows (D2 v3 sequence rows for every non-system role). D2 v3 has no PUBLIC effective row; a missing part is a stop.
- **Referential actions.** For every foreign key whose child is `study_sessions`, and every ancestor reachable through a mutating action (D3 v4 P1, which carries the event kind), the locked file asserts the exact constraint definitions against the re-run result. A parent key update or delete that can mutate `study_sessions` is an **indirect UPDATE or DELETE path**. **VERIFIED, saved live evidence (T-001 FU6-P1, 06/10/2026):** `study_sessions` is reached at depth 1 from `auth.users` through `study_sessions_user_id_fkey`, so deleting an authentication user deletes that user's sessions; and `admin_delete_user_data` (saved J2c; called by `SuperAdminDashboard.jsx`) deletes user data. - **Outcomes if the precondition fails:**

B-04b does not proceed meanwhile;

Binding conditions (QA Rounds 16 and 18):** (1) **Provenance that a plain delete cannot satisfy and that no routine can imitate.** A removal is accepted as account deletion only if both hold at the cutover: (a) **the owning account no longer exists** (the cutover recomputes the canonical token for every `auth.users.id` and requires that no live row produces a removed session's `owner_token`); and (b) **the exact cascade foreign key is intact**: `study_sessions_user_id_fkey` has the same OID as recorded at B-04a, the recorded definition hash, delete action `c`, is validated, and its referential-integrity system triggers are enabled. ## 7. B-05 `flashcards` and `notes`
**Principle.** `target_course` (T) is a derived label for platform rows (brief B 6.3). A row is *platform* when it has a subject S or a discipline D. DS is the discipline of S; name(X) the exact discipline name. An unknown S or D raises a clear error. The trigger fires only when S, D or T is inserted or `IS DISTINCT FROM` its old value.

**Conflict test (NULL-safe, `IS DISTINCT FROM` throughout).** A stored row is a *conflict* if: S is not NULL and ((D IS NOT NULL AND D IS DISTINCT FROM DS) OR T IS DISTINCT FROM name(DS)); or S is NULL and D is not NULL and T IS DISTINCT FROM name(D). A NULL T on a platform row is therefore a conflict. (D2 counts the rows that meet this definition.)

**Precedence.** (1) On UPDATE, evaluate the **OLD row** first. If it is a conflict and any of S, D, T changed, the update is **refused** with a clear message ("flagged as a conflict; reconciliation is a separate reviewed fix"). It is never accepted and never repaired (brief B 6.2). Updates that change none of S, D, T do not fire the trigger and succeed. (2) Otherwise apply the after-state rows below.

| After-state (non-conflict rows, and every INSERT) | Result |
|---|---|
| S set | If D is explicit (inserted non-NULL, or changed) and not NULL and D IS DISTINCT FROM DS: **refuse**. Otherwise D := DS and T := name(DS). Covers INSERT with S; S only; S+T; S+D with D = DS; S+D+T; D changed to NULL with S set; T only on a row with S (the current batch edit sends S and T together, `MyFlashcards.jsx:463`) |
| S NULL, D NULL, T resolves to a discipline name (`resolve_canonical_course_label` exact match) | D := that discipline, T := its exact name |
| S NULL, D NULL, T anything else | untouched (custom course or unassigned) |
| S NULL, D explicit non-NULL | platform by discipline: T := name(D); D must exist |
| S NULL after the operation, D carried unchanged, and S changed to NULL or T changed (platform-to-custom or platform-to-discipline-only edit, or a T-only edit of a discipline-only row; the screens do not send D) | resolve the new T: a discipline name gives D := that discipline, T := exact name; any other T gives D := NULL and T stored as supplied. If T is unchanged: T := name(D) |
| none of S, D, T changed | not fired |
