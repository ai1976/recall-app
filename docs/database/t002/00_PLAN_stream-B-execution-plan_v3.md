## 5. `study_sessions`
### 5.1 B-04a, compatibility
- **Columns (nullable):** `classification`, `discipline_id`, `subject_id`, `custom_course_label`, stored generated `custom_course_key`, `custom_subject_label`, stored generated `custom_subject_key`.
- **Keys:** `discipline_id -> disciplines(id)` and the composite `(discipline_id, subject_id) -> subjects (discipline_id, id)` (new unique constraint on `subjects`), both `NOT VALID`, same column order. Tests: course-only valid row accepted; non-existent discipline refused; valid pair accepted; mismatched pair refused.
- **Shape constraints (`NOT VALID`):** classification is `platform`, `custom`, `general` or NULL. **NULL classification requires `discipline_id`, `subject_id`, both labels NULL.** `platform`: `discipline_id` required, labels NULL. `custom`: `custom_course_label` required, `discipline_id` and `subject_id` NULL. `general`: all NULL. `source` in (`study_mode`, `practice_mode`) requires NULL classification. Not here: "manual requires classification" (B-04b).
- **Label rules by namespace (NB1).** The insert trigger trims **both** labels and refuses an empty value, over 120 characters, or a control character. The refusal of a label whose `normalize_course_text` equals any discipline name (active or inactive) applies to `custom_course_label` **only**, not to `custom_subject_label`. A match to a CMA/CS catalogue label in `custom_course_label` is stored in canonical text. If D3 finds an update path that can touch these columns the trigger also covers `UPDATE OF` them; if none, the plan states that clients hold no UPDATE (RUN 3) and D3 proves no other path.
- **Compatibility, with limit.** VERIFIED in code: the frontend writers are `src/contexts/StudyTimerContext.jsx:214` (columns: `user_id`, `started_at`, `ended_at`, `duration_seconds`, `session_date`, `source`, `category`) and `src/lib/studyTracker.js:120` (adds `session_id`; no category). Neither sends any new column or `created_at`. This is code at one commit; the real-role TEST replays each exact column list as an `authenticated` insert; DB-side writers are D3, edge-function and re-parsed frontend writers are D4.
- **Lock and bounds.** The stored generated columns rewrite the table under `ACCESS EXCLUSIVE`. The file sets `lock_timeout` and `statement_timeout` first; on timeout the single transaction aborts with nothing applied; retried at a quiet time. D2 supplies relation size.
- **No-backfill proof.** A hash over an explicitly ordered projection of the pre-existing columns, keyed by `id`, for rows existing before the run, before and after; new columns asserted NULL separately.
- **Proof ownership.** B-04a-TEST proves the database contract only; the four UI paths are proved at Gate 5 (diff) and Gate 7 (live).
- **Rollback and its residue (NB2).** After F1 a plain drop of the columns would discard captured identity. The ROLLBACK first creates, if absent, `public.t002_study_sessions_classification_archive` (owner = migration owner, RLS enabled with no policy, all client privileges revoked), copies `id` and every classification column of rows with non-NULL classification using `INSERT ... ON CONFLICT (id) DO NOTHING` (idempotent on retry), checks archive count equals source count, and only then drops. The archive is an **intentional rollback residue**: the exact-baseline comparison excludes this one named object, and its later restore or deletion is a separate Founder decision recorded in the rollback TEST.

### 5.2 B-04b, enforcement (DEC-1)
- **Rule:** a `source = 'manual'` row requires a non-NULL classification. Mechanism: **the approved plain CHECK** `CHECK (source IS DISTINCT FROM 'manual' OR classification IS NOT NULL) NOT VALID` (brief B 4.2, B-I5). The expression is two-valued, so a NULL `source` cannot yield UNKNOWN; D2 reports whether `source` can be NULL and the TEST attempts such an insert.
- **Precondition for the CHECK: no update path of any kind.** D3 must classify every path that can UPDATE `study_sessions` (routines, trigger functions, views and rules, scheduled jobs, edge functions per D4, owner or service roles) and list every unresolved lead. The CHECK is used only if there is **no update path and no unresolved lead**. Under the CHECK a legacy manual/NULL row can never be updated by anyone; the TEST states and proves it. **If any update path exists or any lead is unresolved, work on B-04b stops** and the case returns to the Founder: a revised brief B would have to replace the CHECK by a transition-aware rule (refuse an INSERT or UPDATE that newly produces a manual/NULL row; allow an unrelated update of a row that was already legacy), which needs a new brief hash and Gate 1. No fallback is authored in advance.
- **Boundary without a clock.** Because clients hold no DELETE (RUN 3; D3 confirms no other delete path), the set of `manual` rows with NULL classification only grows. The cutover compares **sets**, not dates: a baseline set (ids, count, `sum(duration_seconds)` and the ordered-projection hash) is recorded at the observation start; the observation is "the set is unchanged". D2 also reports whether `created_at` and `id` are server-controlled; `created_at` is used only as an **advisory** list of suspect rows, never as the proof.
- **Order and three timestamps (NB4).** (1) F1 served-version time. (2) The deliberate Gate 7 tests: a log made in a tab opened before the F1 deploy, and a pending log stored by the old version and restored after the upgrade; these create real manual/NULL rows by design; ids recorded; completion time recorded. (3) Observation start: the baseline is taken after (2), includes the recorded test rows by id, and rows between (1) and (3) that are not test rows are listed to the Founder before the baseline is accepted. The test rows belong to the test account `TestOutlook`; their effect on the "legacy" group is a named, accepted residual unless the Founder orders a separately reviewed data fix first. Only then does the window run (length set by the Founder; 14 days is a minimum, not proof).
- **Atomic cutover.** B-04b begins with `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` under `lock_timeout`, then a `DO` block that raises and aborts if the current set differs from the recorded baseline, then `ADD CONSTRAINT`, all in one transaction. Nothing can commit an insert between the check and the rule because the lock is held until the transaction ends. The SQL editor is a single session, so the concurrent-insert behaviour is argued from lock semantics and is `NOT COVERED` by test unless the Founder approves a two-connection run in a non-production database.
- **Closure of old writers (DEC-1), evidence list:** the F1 deployment record (commit SHA, served time); version evidence as in 4(2) for F1; the stale-tab and restored-pending-log tests; the unchanged-set observation; the atomic check. The never-reloaded-tab residual (a refused log) is shown to the Founder, who accepts or defers.
- **Report meaning.** After B-04b is verified, manual/NULL rows are the pre-change rows plus the named test rows, so "Unassigned / legacy" keeps its meaning; only then does B-06b ship.
- **B-04b-TEST:** manual NULL-classification refused; classified manual accepted; `study_mode`/`practice_mode` NULL accepted; NULL-`source` attempt; legacy-row update behaviour as the CHECK implies; counts and projection hash unchanged.

## 7. B-05 `flashcards` and `notes`
**Principle.** `target_course` (T) is a derived label for platform rows (brief B 6.3). A row is *platform* when it has a subject S or a discipline D. DS is the discipline of S; name(X) the exact discipline name. A pre-existing **conflict row** (S set and D set with D <> DS; or S set and T <> name(DS); or S NULL, D set and T <> name(D)) is **never rewritten** (brief B 6.2): it is validated as supplied. The trigger fires only when S, D or T is inserted or `IS DISTINCT FROM` its old value. An unknown S or D raises a clear error.

| Case | Result (non-conflict rows) |
|---|---|
| S set (after the operation) | If D is explicit (inserted non-NULL, or changed) and not NULL and D <> DS: **refuse**. Otherwise D := DS and T := name(DS). Covers INSERT with S; S only; S+T; S+D with D = DS; S+D+T; D to NULL with S set (D := DS); T only on a row with S (T := name(DS); the current batch edit sends S and T together, `MyFlashcards.jsx:463`) |
| S NULL, D NULL, T resolves to a discipline name (`resolve_canonical_course_label` exact match) | D := that discipline, T := its exact name (a card with a custom subject on a platform course keeps the platform identity) |
| S NULL, D NULL, T anything else (custom course or unassigned) | untouched |
| S NULL, D explicit non-NULL (inserted, or changed) | platform by discipline: T := name(D); D must exist |
| **S NULL after the operation, D carried unchanged, and S changed to NULL or T changed** (a platform-to-custom or platform-to-discipline-only edit, or a T-only edit of a discipline-only row; the screens do not send D) | resolve the new T: a discipline name gives D := that discipline, T := exact name; any other T gives D := NULL and T stored as supplied (a custom course). If T is unchanged the row stays platform by D: T := name(D) |
| none of S, D, T changed (including every update of other columns) | not fired |
| Conflict row, any change of S, D or T | accepted only if the resulting triple is consistent as supplied; otherwise refused; never silently repaired |

Every row of the table, and every combination of changed columns (the seven non-empty subsets of {S, D, T}) with valid, NULL and unknown identifiers, is a TEST case. The table may be corrected by D4 evidence **before B-05 is authored** (if a writer shows a transition the table misreads, the table changes; it is not frozen). The notes path is checked column by column against D2 before assuming it matches `flashcards`.
- **Legacy conflicts.** F6 measured 0; D2 recounts including the S NULL / D set case. If 0, a conflict fixture is built **inside the rollback-only TEST** under the owner (not as a real-role step): disable only the exact new B-05 trigger, hold the required lock, insert the conflicting row, re-enable the trigger, prove every other guard stayed enabled and that the trigger state is restored after each intentional error path (re-asserted at the end of the test). If QA does not approve the technique the case is `NOT COVERED`; it never justifies a repair policy.
- **Due invalidation.** The trigger can change `flashcards.target_course` after an S-only or D-only update. F0 extends the due guard and wrappers (2); B-05 does not execute before F0 is live; F1 adds a subject-only transition test (an update outside the wrapper fails the build; through the wrapper it notifies).
- **Foreign keys:** composite `NOT VALID` on both tables; TEST proves legacy rows (NULL D) are skipped and updates not touching the key columns skip the check (brief B 6.3).
- Coexistence with `trg_guard_flashcards_is_verified`, `trg_guard_flashcard_batch_move`, `trg_guard_notes_privileged_columns` and the AFTER counters `trg_aaa_counter_flashcards`, `trg_badge_flashcard_create`, `trigger_update_deck_card_count`, by exercised paths and name order.
