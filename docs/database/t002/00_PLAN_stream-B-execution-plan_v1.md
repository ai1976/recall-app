## 4. `study_sessions` (B-04a and B-04b)
### 4.1 B-04a, compatibility (current frontend keeps working)
- Adds the classification columns of brief B 4.1 (all nullable): `classification`, `discipline_id`, `subject_id`, `custom_course_label`, stored generated `custom_course_key`, `custom_subject_label`, stored generated `custom_subject_key`. Adding stored generated columns rewrites the table under an `ACCESS EXCLUSIVE` lock (≈1,395 rows per brief B 4.1, to be re-measured in D2): a timer insert arriving during the run waits briefly; the run is a single short statement set, stated in the file.
- Creates the unique constraint on `subjects (discipline_id, id)` and the composite foreign key `(discipline_id, subject_id)` referencing it, same column order both sides (brief B 4.1), `NOT VALID`.
- Shape constraints of brief B 4.2 (`platform`, `custom`, `general`), **each written to apply only when `classification IS NOT NULL`**, plus "`source` in (`study_mode`, `practice_mode`) requires NULL classification" (the in-app writers send NULL: code `src/lib/studyTracker.js:120`). **Not included:** "`source = 'manual'` requires a non-NULL classification" (that is B-04b).
- Insert trigger: a custom label whose `normalize_course_text` equals the name of **any** discipline (active or inactive) is refused; a custom label equal to a catalogue label (CMA/CS) is stored in canonical text (brief B 5.3a).
- **Why this is safe for the current frontend.** VERIFIED in code: the only two `study_sessions` writers in the frontend are `src/contexts/StudyTimerContext.jsx:214` (manual, `confirmCategory`) and `src/lib/studyTracker.js:120` (in-app). Neither sends a classification column, so every insert has NULL classification and passes every B-04a constraint. This is a code observation; **B-04a-TEST** must additionally replay the exact column list each of the two writers sends (taken from the code at the commit under review) as a real `authenticated` insert and show it succeeds. A DB-side writer (a function, trigger or cron that inserts into `study_sessions`) is searched for in diagnostic D3 before B-04a is authored.
- B-04a-TEST proves: every combination of `source` × classification against the B-04a constraints (accepted and refused cases listed in the file); keys equal `normalize_course_text` of the label and a client cannot set them; the display-label tie-breaker (greatest `created_at`, `id`); label boundaries 0, 1, 120, 121 characters, control character, leading/trailing space, 120 stored untruncated; the four manual paths through the one insert contract; the alias flow of brief B 5.4 (two consecutive logs); **no backfill**: row count and a content hash of all pre-existing rows are identical before and after, and every pre-existing row has NULL in the new columns. It does **not** claim "legacy update succeeds" (finding 4).

### 4.2 B-04b, enforcement (only after the new frontend is live)
- Adds `CHECK (source <> 'manual' OR classification IS NOT NULL) NOT VALID`.
- **What it does to legacy rows (stated, not hidden).** PostgreSQL evaluates a `NOT VALID` check on every new version of a row. A legacy manual/NULL row therefore **cannot be updated by anyone** after B-04b (any `UPDATE`, even of an unrelated column, fails). This is acceptable only if no one updates `study_sessions`: clients hold INSERT and SELECT only (brief B section 2, item 5, RUN 3) and diagnostic D3 must find no routine that updates it. **If D3 finds an updater**, B-04b uses the alternative that exempts legacy rows by construction (`... OR created_at < <cutover timestamp>`), and its TEST states the residual (a client can insert an old `created_at`; the consequence is only an unclassified row, which the report already shows as "Unassigned / legacy"). Which form applies is decided by D3, not assumed.
- **Window before B-04b.** Precondition (PROPOSAL, for the Founder after QA review): at least 14 days after F1 is live and Gate 7 accepted, a read-only count shows **zero** `source = 'manual'` rows created after the F1 deploy time with NULL classification. This covers stale open tabs and browser-stored pending logs written by the old version (restored pending logs end at `confirmCategory`, brief B 4.4, so they are asked for a course at restore; a tab that never reloaded is the residual). If the count is not zero the enforcement stays off and the Founder decides.
- B-04b-TEST: a manual insert with NULL classification is refused; every classified manual insert, and every `study_mode`/`practice_mode` NULL insert, is accepted; an `UPDATE` of a pre-existing manual/NULL row behaves exactly as stated above (refused under the plain form, accepted under the exempt form); row count and content hash unchanged.

## 5. B-07, `access_requests.course` (answer to finding 3)
- **Contract (from brief B 5.1, 5.2, 5.3a):** trim; no control characters; length 1 to 120; never truncated; a normalized match to a discipline name (active or inactive) is rewritten to that discipline's exact stored name; a match to a CMA/CS catalogue label is rewritten to its canonical text; anything else is stored trimmed.
- **Mechanism (PROPOSAL, differs from the wording of brief B 5.3a only in where the code lives):** a BEFORE INSERT OR UPDATE OF `course` trigger on `access_requests`, firing only when the value is inserted or changes, using the same `resolve_canonical_course_label` as B-03. Brief B 5.3a lists `submit_access_request` as a caller of the resolver; a table trigger gives the same stored result for **every** writer, and, because `submit_access_request` is rewritten wholesale by A-10c, a function-body change would be silently lost there. The trigger lives on the table and survives A-10c. If QA prefers the function-body form, B-07 becomes a `[FUNCTIONS]` file that A-10c must carry; the trade-off is stated for QA to rule on.
- **Compatibility with the current frontend.** The course value is written only through the RPC `submit_access_request` (VERIFIED in code: `src/lib/dueSet.js:103`); `AdminDashboard.jsx` reads the table (line 271, `select('*')`) and updates only `status` (line 305), so neither touches `course`; DB-side writers are D3. Existing rows are untouched (the trigger fires only on insert or a change of `course`): brief B 5.3b measured 5 exact and 1 other value (follow-up G1). A value that now violates the rule (over 120 characters or a control character) is **refused**; from the current form this reaches the user as an error from the RPC. This is a deliberate new refusal on a free-text field; measured maximum length of existing values is 19 characters (F9, profiles) and the form's own limit is OPEN, listed in D2.
- **Coexistence.** `access_requests` triggers (existing and A-10a's target-validation and immutable-`submitter` triggers) fire in name order; B-07's touches only `course`. B-07-TEST proves coexistence with the **existing** triggers now (from D2) and the same coexistence test is added to A-10a/A-10c when they land (section 9).
- B-07-TEST: exact, case-variant and repeated-whitespace values stored canonically; CMA/CS label canonical; custom label stored trimmed; boundary cases 0/1/120/121, control character; unrelated update of a legacy row succeeds; `UPDATE OF course` with an unchanged value does nothing; real `anon` caller through `submit_access_request`.

## 6. B-05 `flashcards` and `notes`: derive, not require (answer to finding 1, second sentence)
- **Facts (brief B 6.2, follow-up F6 and G1; to be remeasured in D2):** `discipline_id` is NULL on all 2,850 flashcards and all 128 notes; every flashcard has a subject whose discipline name equals its `target_course`; 125 of 128 notes have a subject and match; 3 notes have neither subject nor discipline.
- **Behaviour:** on INSERT, and on UPDATE of `subject_id`, `discipline_id` or `target_course`: if `subject_id` is NOT NULL, derive `discipline_id` from `subjects.discipline_id`; refuse an explicitly supplied `discipline_id` that disagrees with it; set `target_course` from the discipline name (a derived label, brief B 6.3). If `subject_id` is NULL and `discipline_id` is NULL, do nothing (custom or unassigned rows, including the 3 legacy notes). The trigger **does not require** a client to send `discipline_id`, so no current writer changes.
- **Open risk, stated:** deriving `target_course` from the subject overwrites a client-supplied `target_course` that disagrees with the subject. Whether any current writer relies on a different `target_course` is **OPEN** and is exactly what D3's writer scan and B-05-TEST's writer matrix must answer before the file is authored. Frontend writers found by grep today (code, to be re-confirmed at the commit under review): `FlashcardCreate.jsx:657`, `BulkUploadFlashcards.jsx:806`, `NoteEdit.jsx` (several), plus the note upload and admin pages, and the move/visibility updates in `src/lib/dueSet.js`. DB-side writers (functions, triggers) come from D3.
- **Legacy rows:** an unrelated update of a legacy card or note (no `discipline_id`) succeeds; the trigger derives but never refuses a row that is consistent. The derive-on-update clause fires only when the three named columns are in the `SET` list **and** a value changes (so `dueSet.js` updates of `visibility`, `batch` moves and deletes never reach it). A legacy row whose subject-derived discipline disagrees with its `target_course` would be rewritten only if one of the three columns is touched; F6 measured 0 such rows.
- **Composite foreign keys** `NOT VALID` on both tables, as v5. MATCH SIMPLE skips the check when any key column is NULL; B-05-TEST proves a legacy row (NULL `discipline_id`) is unaffected and that updates not touching the key columns skip the check (brief B 6.3 asked for this confirmation).
- **Coexistence.** Must be reviewed against the saved live trigger bodies (H3) and PostgreSQL's name-ordered BEFORE firing: `trg_guard_flashcards_is_verified`, `trg_guard_flashcard_batch_move`, `trg_guard_notes_privileged_columns` and the AFTER counters `trg_aaa_counter_flashcards`, `trg_badge_flashcard_create`, `trigger_update_deck_card_count`. B-05-TEST shows coexistence by exercising each guarded path with the new trigger present, not by listing it.

4. **Exact test cases in the scope claimed.** An inactive-course, conflict, over-limit, boundary or role case that live data does not contain is reported **NOT COVERED** until a safe fixture is approved or the Founder accepts the named residual; a zero count is never behavioural proof. Complete-set comparisons are deterministic.
5. **Rollback** covers definitions, signatures, owner, configuration/search path, dependencies and exact ACLs, compared by **normalised semantics** (CRLF and `search_path` spelling), not by raw body hash. A rollback never used in a verified run does not receive Gate 4.
6. **Slice 1 preservation surface.** Before/after outputs under real roles for `fn_due_eligible_dates`, `get_due_forecast`, `get_due_forecast_buckets`, `get_study_heatmap_split`, the atomic due snapshot, `get_study_time_stats`, and the professor batch reports. A failed or empty first load stays unknown/neutral and never shows a false zero, an empty course group or a calm state.
7. **SQL is read as a parser would** (CTE boundaries, `UNION`, `WITH RECURSIVE`, name/text types, brackets, quotes, regex samples) before each file is presented, and the round says so. Claude has no database engine; nothing here has been run.
