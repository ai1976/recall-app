# T-002 stream B read-only diagnostic batch, proposal v1 (a list, not SQL)

**Status:** written 08/10/2026 in T-002 Round 13. It lifts section 11 of plan v5 (`8b08be4c87ae`) out into its own file so QA can accept it, or return it, **on its own**, separately from the plan. It authorizes nothing: no SQL exists and none was run. If QA accepts this list, Claude writes the SQL (and the D4 script) as new files, QA audits each by exact hash, and the Founder runs the SQL once per stage, saving every raw result unchanged under `docs/discussions/evidence/`.

**Why now.** Most open items in the plan (B-04b form, B-06c, the conditions of B-03/B-07, the ACL ceilings) are decided by facts that nobody has measured yet. These diagnostics are read-only and decide those items; running them earlier shortens the finish line.

**Rules for every diagnostic (from the Round 1 working rules and QA's conditions).** Read-only: nothing writes, and the Supabase editor's single transaction is used with `SET TRANSACTION READ ONLY` as its first statement where a database call is made (D1b: before the role and claims are set). Output is aggregate or catalogue data; no user email, user id or card text is saved. A scheduled-job command is never emitted raw (secrets): only a safe hash, the schedule and structural flags. An error, truncation or reconciliation mismatch stops the run and is saved unchanged. Absence of a constraint, trigger, policy or grant is concluded only from the system catalogue, never from code.
