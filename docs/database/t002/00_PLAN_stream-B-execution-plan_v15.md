### 5.2 B-04b, enforcement (DEC-1, DEC-3, DEC-4 simplified)
- **Rule and mechanism:** a `source = 'manual'` row requires a non-NULL classification, as the approved plain CHECK `CHECK (source IS DISTINCT FROM 'manual' OR classification IS NOT NULL) NOT VALID` (brief B 4.2, B-I5). The expression is two-valued; D2 reports whether `source` can be NULL and the TEST attempts such an insert.
- **Precondition, with separate outcomes.** D3 and D4 classify every **discovered** path that can ADD or RELABEL a `study_sessions` row (INSERT, UPDATE, UPSERT, MERGE, COPY): application code, edge functions, routines, trigger functions, rules and views, scheduled jobs, foreign-key referential actions whose result is an UPDATE (SET NULL, SET DEFAULT), and any approved operational procedure (the single data fix below is one and ends before B-04b). The plain CHECK is used only if **every such path is accounted for (allowlisted or closed) and no lead that could perform one of them is unresolved**. DELETE and TRUNCATE paths (including account deletion) only remove rows; they are recorded in the matrix as information and do not stop the cutover.
- **Role universe and effective capability (P4).** Capability is judged on **effective** privilege (D2 v3 P4: `has_table_privilege` and `has_column_privilege`, which follow membership and inheritance, with `PUBLIC` read from the ACL, never passed to those functions), never on ACL rows and never on a role attribute. **`BYPASSRLS` is reported as a row-level-security fact only: it grants no privilege by itself.** The universe is `PUBLIC`, `anon`, `authenticated`, `service_role`, `authenticator`, and every non-system role that is a member of one of them or that D2 shows holding UPDATE, DELETE or TRUNCATE on `study_sessions`. **Required (gating):** zero effective UPDATE (table-level and column-level) for `PUBLIC`, `anon`, `authenticated` and every role inheriting from them, **and for `service_role`**. **Reported, not a stop (DEC-4):** effective DELETE or TRUNCATE for any of them is listed as a finding in the Gate 3 request. **Operation-specific rule for `service_role`:** INSERT and SELECT may be retained if D4 names an edge function that needs them; an edge function that needs UPDATE on `study_sessions` is **not** a retention reason, it produces the corresponding stop outcome below (DELETE and TRUNCATE needs are reported). **Accepted, reported residual (capability by ownership or superuser, not removable by an ACL change):** the table owner and superusers, and the operational principals and known runbooks that can use them: the Supabase SQL Editor role, the CLI login role and the single data fix of this plan. **What stops the cutover:** any client-facing role with effective capability; any scheduled job, routine or trigger that D3 shows performing an UPDATE through such a principal; any unresolved lead. The residual list is written into the Gate 3 request. **The zero-capability assertion is exactly the conjunction of three parts (D2 v3 output):** (a) every real role outside the allowlisted owner/superuser residual has `false` for every effective table-level and column-level UPDATE, DELETE and TRUNCATE row; (b) the ACL-derived PUBLIC section (grantee 0) lists none of those privileges, table-level or column-level; (c) no non-system role holds a sequence privilege beyond what the plan allows (D2 v3 sequence rows for every non-system role). D2 v3 has no PUBLIC effective row; a missing part is a stop.
- **Referential actions.** For every foreign key whose child is `study_sessions`, and every ancestor reachable through a mutating action (D3 v9 P1, which carries the event kind), the locked file asserts the exact constraint definitions against the re-run result. A parent key update or delete that can mutate `study_sessions` is an **indirect UPDATE or DELETE path**. **VERIFIED, saved live evidence (T-001 FU6-P1, 06/10/2026):** `study_sessions` is reached at depth 1 from `auth.users` through `study_sessions_user_id_fkey`, so deleting an authentication user deletes that user's sessions; and `admin_delete_user_data` (saved J2c; called by `SuperAdminDashboard.jsx`) deletes user data. D2 and D3 re-confirm both live.
- **Outcomes if the precondition fails:**
  - **an UPDATE path:** work on B-04b stops and returns to the Founder; a revised brief B would replace the CHECK by a transition-aware rule (refuse an INSERT or UPDATE that newly produces a manual/NULL row, allow an unrelated update of an already legacy row), needing a new brief hash and Gate 1;
  - **a DELETE or TRUNCATE path (including account deletion, cascade from `auth.users` and `admin_delete_user_data`):** informational only (DEC-4). It cannot create an unclassified row. The client-privilege hygiene below (no client DELETE or TRUNCATE, per RUN 3) stays as stated, but a deviation is a finding, not a stop for B-04b;
  - **account deletion, DEC-4 (decided by the Founder, 08/10/2026):** accepted without provenance. Deleting a user's sessions can only REMOVE rows. It cannot add an unclassified row or relabel a survivor, so it does not threaten the meaning of "Unassigned / legacy" or the enforcement check. The cutover reports the number of anchor rows that disappeared and the user-visible effect (their legacy hours leave the totals); it does not require that a removal be explained;
  - **an unresolved lead:** treated as an existing path of each of the three kinds until resolved.
- **Set assertion SA (the one comparison used wherever this plan compares the manual/NULL set; removal-tolerant, per id).** Let `C` be the current set of `manual` rows with NULL classification and `A` the anchor, embedded in the locked file as a list of `(id, fingerprint)` pairs, where the fingerprint is the SHA-256 of the canonical text of EVERY column of the row in a frozen column order (frozen at Gate 2 from D2; each value NULL-safe and length-prefixed, so NULL and the empty string differ). SA holds when: (i) every id in `C` is an id in `A` (nothing was added); (ii) for every id in `C`, the current fingerprint equals the embedded one (no surviving row was altered, relabelled or changed in any report field, by any path including an owner or SQL-editor operation); (iii) the embedded list and its overall hash are unchanged in the file. Anchor ids not in `C` are REPORTED and split into `gone` (no row with the id) and `classified` (the row exists and is no longer manual/NULL; expected only for the data fix's test row). Shrinkage is never a failure. B-04b-TEST cases: empty `C`, empty `A`, NULL columns, an altered surviving column (each column in turn), a removed id, an added id, and a same-id reinsertion with different content (fails (ii)) or identical content (indistinguishable, accepted and stated).
- **Fresh closure at the time of B-04b (exact, sink-based).** The initial D2/D3 results predate P1 and F1. The closure is re-run on the live database **after F1 is live and again after the observation window, immediately before Gate 3 and execution**. The locked body of B-04b then asserts, aborting on any difference: (1) **allowlist 1**, each object identified by name, signature and definition hash: the B-04a label/identity trigger function and trigger (the frontend INSERT is a client privilege, not an object); (2) **sinks:** every routine, trigger function, rule, view, scheduled job and foreign-key path that can INSERT, UPDATE, UPSERT, MERGE or COPY `study_sessions` is in the hashed allowlist by its exact key, and every direct D4 code writer of those operations is in `code_writers` with a resolved payload; the matrix has no `unresolved` cell for those operations (a foreign-key path with a UPDATE result, i.e. SET NULL or SET DEFAULT, is a sink; a DELETE result is information); (3) **zero** UPDATE effective capability (table-level and column-level) for the role universe above, and no client INSERT of a manual NULL (the B-04a trigger and F1 govern it); (4) every D3 class compared with the re-run: view and rule dependencies (transitive), dynamic-SQL, unreadable and compiled routines and extensions (each cleared by identity and hash), and scheduled jobs (safe hash and structural flags, with the cron visibility assertion true: a changed job or an unresolved visibility fails); (5) the comparison of the re-run D3 v9 (P1 to P6) and D4 v9 results with the allowlist is produced by `D-05_writer-matrix_v7.mjs` from hashed, schema-validated inputs, and its `result_sha256` is quoted in the Gate 3 request; the locked B-04b embeds the same allowlist values (QA compares them with the hashed allowlist file) and asserts them against the live catalogue; (6) the **deployed application and edge-function commit SHA** is saved from the deployment record and passed to D-05 as `--deployed-commit`; D-05 stops unless it equals the D4 commit; D4 must be taken at a clean commit and its `tool_sha256` must equal the hash recorded in the Gate 3 request (`--d4-tool-sha256`); its file manifest is recomputed by D-05; D4 is re-run if the deployed SHA differs.
- **Canonical key schema (contract; D-05 v7 computes it, the locked B-04b asserts every field live).** Routine `schema.name(args)|src_md5`; writable view and rewrite rule `id|definition_md5`; foreign-key path `foreign_key:<ancestor>:<event>-><result>|path=<edge > edge ...>|depth=<n>`, each edge `<child schema.table>.<constraint>=><parent schema.table>#<md5 of the constraint definition>` (D3 v9 P1 returns one row per path, the ancestor schema-qualified, and the eight canonical target relations); scheduled job `job <id> <name>|command_md5|active|schedule|database|username`; direct code writer `file|table|op|enclosing function`; extension clearance `extension_<dynamic|compiled>:name@version#count|sha256` (SHA-256 over the sorted fully qualified identities and the SHA-256 of each body). Unused allowlist or clearance entries are a stop unless recorded as reviewed in the allowlist file. The allowlist file and the clearances are hashed inputs, and the matrix result carries `result_sha256`.
- **The anchor set A (restores DEC-1's true boundary).** A is the set of `manual` rows with NULL classification that exist when F1 becomes the served version: ids with a per-row fingerprint over every column (SA), count and `COALESCE(sum(duration_seconds), 0)`. S0 is captured **immediately before** the F1 promotion and S1 **immediately after** it, as part of the deployment choreography (section 2), at a quiet time chosen by the Founder; the served time is read from the deployment record. **Clock evidence (retained in the run record):** database-clock samples at S0 and S1, the clock source of the deployment timestamp, and the justified skew margin; `created_at` ownership alone never establishes that the clocks are comparable.
  - If S1 equals S0, A = S0.
  - If S1 contains rows not in S0 (the **delta**), the delta does **not** become legacy by default. A delta row joins A only if a **trustworthy database-authored fact** proves it was written before the F1 served time: D2 must show `created_at` is server-controlled (not caller-supplied), and the deployment time and the database clock must be comparable with a stated margin; rows within the margin are ambiguous. **If this cannot be shown, every delta row is unresolved, not legacy.** The cutover then stops: the rows are resolved only by a separately reviewed action that needs the Founder (a student's intent for a past log cannot be derived by Claude, and an exception to B-I3 would need a revised brief). S1 never silently becomes A.
  - The anchor is fixed at that point; a later snapshot is operational evidence only. Any later non-test manual/NULL row fails SA (i) and is resolved by a separately reviewed action, never absorbed.
- **Tests (part of F1 Gate 7), in this order.** Both old-version states are prepared **before** the F1 promotion (a pending log left unconfirmed in a browser still running the old version; a tab opened on the old version).
  1. **Restored pending log.** Restored after the upgrade, it must pass through the new picker and be stored classified. A manual/NULL row here means **F1 has failed this test**; it is fixed, not tolerated.
  2. **Stale old tab (DEC-3).** A tab opened before the F1 deployment, as `TestOutlook`, submits a log. By design this creates exactly **one** manual/NULL row; its id is recorded.
  3. **Data fix** (a `[DATA]` file, QA-audited by exact hash, gated 2 to 4, run before B-04b exists). Before deleting anything it asserts, in one transaction and aborting on any mismatch: (i) **SA holds with `A ∪ {the recorded test id}` as the permitted set** (nothing else was added; removals from `A` are reported), compared by count, sum and the same per-row SA fingerprint comparison as the cutover (the encoding of the atomic cutover); (ii) the target row has the expected test-account user, `source = 'manual'`, NULL classification and the recorded test duration and time window (a fingerprint recorded at test time); (iii) exactly one row matches. It then archives the **complete row** into an **owner-only archive table** `public.t002_study_sessions_datafix_archive` (RLS enabled with no policy, all client privileges revoked, row in 10B), deletes that row and nothing else (the deletion is recorded in the run record with its transaction id), and re-asserts SA with `A` as the permitted set. **No user id or other row content is written to the repository or to evidence files**: only the row id, a fingerprint hash and counts are recorded. The ROLLBACK restores from the archive by an `INSERT` that **omits the generated key columns** (they recompute) and verifies the recomputed values equal the archived ones, and is allowed only **before B-04b exists**; once the CHECK exists, restoring a manual/NULL row would itself fail, so the **rollback order** is: roll back B-04b first, then restore the row. The archive's retention or removal is a Founder decision after B-04b Gate 4. There is no named exception in the legacy group.
- **Observation** starts after step 3; the Founder sets the length (14 days is a minimum, not proof); **SA must hold throughout** (deletions in the window, account deletions included, shrink the set and are reported; nothing may be added). Three timestamps and the test row id are recorded separately: the F1 served time, completion of tests and data fix, and the observation start.
- **Atomic cutover.** B-04b begins with `LOCK TABLE ... ## 7. B-05 `flashcards` and `notes`
**Principle.** `target_course` (T) is a derived label for platform rows (brief B 6.3). A row is *platform* when it has a subject S or a discipline D. DS is the discipline of S; name(X) the exact discipline name. An unknown S or D raises a clear error. The trigger fires only when S, D or T is inserted or `IS DISTINCT FROM` its old value.

**Conflict test (NULL-safe, `IS DISTINCT FROM` throughout).** A stored row is a *conflict* if: S is not NULL and ((D IS NOT NULL AND D IS DISTINCT FROM DS) OR T IS DISTINCT FROM name(DS)); or S is NULL and D is not NULL and T IS DISTINCT FROM name(D). A NULL T on a platform row is therefore a conflict. (D2 counts the rows that meet this definition.)

**Precedence.** (1) On UPDATE, evaluate the **OLD row** first. If it is a conflict and any of S, D, T changed, the update is **refused** with a clear message ("flagged as a conflict; reconciliation is a separate reviewed fix"). It is never accepted and never repaired (brief B 6.2). Updates that change none of S, D, T do not fire the trigger and succeed. (2) Otherwise apply the after-state rows below.

| After-state (non-conflict rows, and every INSERT) | Result |
|---|---|
| S set | If D is explicit (inserted non-NULL, or changed) and not NULL and D IS DISTINCT FROM DS: **refuse**. Otherwise D := DS and T := name(DS). Covers INSERT with S; S only; S+T; S+D with D = DS; S+D+T; D changed to NULL with S set; T only on a row with S (the current batch edit sends S and T together, `MyFlashcards.jsx:463`) |
| S NULL, D NULL, T resolves to a discipline name (`resolve_canonical_course_label` exact match) | D := that discipline, T := its exact name |
| S NULL, D NULL, T anything else | untouched (custom course or unassigned) |
| S NULL, D explicit non-NULL | platform by discipline: T := name(D); D must exist |
| S NULL after the operation, D carried unchanged, and S changed to NULL or T changed (platform-to-custom or platform-to-discipline-only edit, or a T-only edit of a discipline-only row; the screens do not send D) | resolve the new T: a discipline name gives D := that discipline, T := exact name; any other T gives D := NULL and T stored as supplied. If T is unchanged: T := name(D) |
| none of S, D, T changed | not fired |
