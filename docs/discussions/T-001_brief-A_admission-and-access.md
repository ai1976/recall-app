## 1. Invariants (every other artifact must respect these)
- **A-I1.** The only authoritative identity of a person is `auth.uid()`. A typed email, a ref token and an invite token are **claims**, never identity.
- **A-I2.** A claim becomes an authoritative link only by verification: (a) the claiming account's **confirmed** account email equals the request's contact email, or (b) an administrator explicitly confirms it. Until then it grants, closes and merges nothing. A claim never blocks another account's claim, and every administrator link change is audited and recoverable (4.3).
- **A-I3.** No access request row is ever discarded or suppressed because of an unverified email. Repeats are grouped in the admin display and admin notifications are throttled; every row is stored.
- **A-I4.** Collapsing a duplicate request is allowed only for a requester stored from `auth.uid()` at submission (A-I1) and the same request target (section 3), through the two indexes of 4.2, which cover only rows whose requester was set by the server (basis `submitter`). Legacy requester ids were client-supplied; they are outside the indexes and are not links (4.4).
- **A-I5.** Closing a request happens only through an authoritative link or an explicit administrator selection, never through a broad email match.
- **A-I6.** Rejection, removal and leaving **preserve** the membership row; history is append-only; no row presence confers access: only status `active` does.
- **A-I7.** Batch membership and content entitlement are separate. One server-side eligibility rule (section 7) is invoked at **every** transition that creates a request or makes a student active, including activation by invite link; section 6.2 marks each such transition.
- **A-I8.** Invites are enforced atomically on the server. One lock order applies to every writer (section 6.6).
- **A-I9.** No in-app payment in v1. Manual grants are called "creator-granted" or "externally fulfilled", never "paid", unless a real transaction is recorded.
- **A-I10.** Existing shared batch links keep working through the migration.
- **A-I11.** Every relation this brief adds (claims, invites, membership events) has row-level security enabled, **no client policies and no direct client privileges** (explicit revoke, never default grants), and is read and written only through SECURITY DEFINER functions. **For every such function, default and `PUBLIC` execution is revoked first and `EXECUTE` is then granted only to the roles listed for it (`anon` only where the function is explicitly listed for it, which in this brief is `get_group_preview` alone), an internal authorization check, a pinned `search_path`, and a stated caller scope and returned-field scope** (claims: 4.7; invites: section 5; events: 6.4). A catalog test fails if any of these relations carries an `anon`, `authenticated` or `PUBLIC` grant, or if any of these functions is executable by a role not listed for it, or not executable by a role listed for it (so the test never both requires and forbids the preview grant).

## 2. Defects the evidence proves
1. **Correlation and display, not absence of links.** A batch request is reliably keyed to the student's profile (`study_group_members.user_id`, foreign key, RUN 6). An access request can carry an email, a client-supplied `requester_user_id` and a ref-token correlation. The live `submit_access_request` stores whatever requester id the client sends (RUN 1A); the admin screen matches only on exact client-side email or ref-token comparison and ignores `requester_user_id` (`AdminDashboard.jsx:1386-1389`); `link_access_request` lets any signed-in user set `profiles.access_request_ref` once to any uuid (RUN 1A). The admin screens do not join or display the relationships (matrix rows 3, 8, 10, 20).
2. "Joining a batch" and "having content access" are separate in the data but promised together in the wording (rows 4, 6, 9).
3. The invite is a permanent, unlabelled token with no recipient, no expiry, no revocation and no UNIQUE constraint (RUN 6).
4. Rejection, removal and re-request leave no durable trace; removal and rejection notify nobody (rows 5, 17).
5. Granting access never closes the request (RUN 1A, RUN 7: 6 requests all `pending`, 240 enrolled students); duplicates are not controlled.
6. The Tier B content lock is located only in the screens (`NoteDetail.jsx:166`, `StudyMode.jsx:515-518`). **VERIFIED not enforced in the database (follow-up F2, F3B, F4, 04/10/2026):** no policy mentions `account_type`; only four functions do (`admin_bulk_add_to_batch`, `admin_grant_access`, `fn_create_profile_on_signup`, `fn_guard_profiles_protected_columns`); `get_browsable_notes` and `get_browsable_decks` gate by visibility, group share and course text, never by account type; public notes and flashcards are readable under the `public` policies.

## 3. Request target (the term "scope" is not used)
A **request target** is the triple (`request_type`, `content_type`, `content_id`) already stored on `access_requests`. For this brief only `request_type = 'student_access'` is in play. Its targets are: **platform-level** (no content item: account-level full content access) or **one content item** (`content_type` note or flashcard_deck, with its `content_id`, as the preview wall stores today). `institute_inquiry` and `educator_application` are out of scope. A later creator-access epic adds creator targets; this brief does not.
**Valid target shapes for `student_access`:** *platform-level* = `content_type` and `content_id` both NULL; *item-level* = both present, `content_type` is `note` or `flashcard_deck` (the live `access_requests_content_type_check` allows exactly those two values and NULL, RUN 7), and `content_id` is an existing `notes.id` or `flashcard_decks.id` respectively (VERIFIED-in-repo: `NoteDetail.jsx:327-330` passes the note id; `StudyMode.jsx:296,339-341,1075` passes the deck id). Any other combination, such as one field present and the other NULL, is **malformed** and refused. Live facts: the only constraint on these columns is the `content_type` check; there is no pair rule and no foreign key (`content_id` is a polymorphic `uuid`; the live `submit_access_request` stores both as sent, RUN 1A). Whether legacy rows are malformed is measured by RUN F8.
**Open** means status `pending` or `contacted` (the two statuses of `access_requests_status_check` that still await a decision, RUN 7). Granting platform access (the existing `admin_grant_access`) satisfies every open `student_access` request of that account, whatever its content target.

## 4. Access-request contract
**4.1 At submission.**
- Signed-in caller: the requester stored is `auth.uid()` (a client-supplied requester id is ignored) and the request's **link account** (4.3) is set to `auth.uid()` with basis `submitter`, because the caller's own authenticated act is the strongest link there is.
- Anonymous caller (logged-out visitor; `PUBLIC`/`anon` EXECUTE stays because logged-out visitors use the wall): no requester is stored.
- The typed email is normalized (trimmed, lower-cased) and stored as the **contact email**. It is a claim (A-I1).
- If a signed-in caller's contact email differs from their account email, the row is flagged "contact email differs from account email" for the admin. No link to any other account is made.
**4.2 Duplicates (A-I3, A-I4).**
- **Trusted requester rows only (signed in at submission, A-I1):** at most one **open** request per (trusted requester, request target). A unique index treats NULLs as distinct, so one ordinary index over (requester, request type, content type, content id) would **not** stop repeated platform-level requests, whose content fields are both NULL. The contract is therefore **two partial unique indexes**, both limited to rows with `request_type = 'student_access'`, status open and **link basis `submitter`** (4.3): (i) **platform-level**: unique on (link account) where `content_type` and `content_id` are both NULL; (ii) **item-level**: unique on (link account, content type, content id) where both are not NULL. Both are keyed on the **link account of a `submitter` row**, not on `requester_user_id`, because every row written before this change may carry a client-supplied requester id (RUN 1A) and must never take part in deduplication.
- **Provenance of `submitter` (immutable, server-set).** The basis `submitter` is written only by `submit_access_request`, in the same INSERT that stores the requester and the link account, and only from `auth.uid()` of a signed-in caller. A trigger guarantees that a row can never be given the basis `submitter` by an UPDATE, that the basis, link account and requester of a `submitter` row can never be changed afterwards (including by a SECURITY DEFINER administrator function), and that an INSERT with that basis is refused unless the link account equals both the requester and `auth.uid()`; client roles hold no write privilege on the link columns (to be proved by real-role tests; the columns do not exist yet, so RUN F1 cannot show it). **The trigger and the privileges do different jobs:** the trigger would accept a direct INSERT whose basis, link account and requester all equal the caller, so "written only by `submit_access_request`" is true only if client table writes are denied. A column-level revoke is **not** sufficient while a table-level INSERT or UPDATE grant is still effective; the SQL gate must either make the function the only write path (no client INSERT or UPDATE on `access_requests`) or replace table grants with an explicit allowlist of safe columns, and the tests must attempt a direct table INSERT and UPDATE as a real `authenticated` caller. Every row that exists when this change ships has no basis, so **legacy rows are outside both indexes**: an untrusted legacy id can neither collide with, suppress nor be returned as a genuine person's duplicate, and no legacy cleanup is needed for index creation. Legacy requester ids stay stored, are shown to the administrator as "unverified id", and are never a link (4.4).
- `NULLS NOT DISTINCT` is available (PostgreSQL 17.6, G5) and would be an acceptable single-index alternative; the two partial indexes are kept because the `submitter` predicate needs a partial index anyway. Other request types lie outside both indexes. A repeat by the same signed-in person returns the existing open `submitter` request; `submit_access_request` handles the race by catching the unique violation and returning the existing row, which by the index predicate is always a trusted row.
- **Target validation.** `submit_access_request` validates the shape of section 3 before inserting, and a trigger that fires on insert and only when `request_type`, `content_type` or `content_id` changes enforces the same rule for any other writer (including a direct client insert if F1 shows one is possible). It is a trigger and not a table CHECK for the reason stated in brief B 5.3: a CHECK is evaluated on every update, so one legacy malformed row would block ordinary administrator status changes. Existing legacy duplicates and malformed rows are left as they are (RUN F8 sizes them); they are not a precondition for the indexes because the indexes exclude them.
- Anonymous: **never deduplicated or suppressed**. The admin screen groups anonymous repeats by contact email and target with a count; admin notifications are throttled to one per (contact email, target) per 24 hours; every row is stored.
- Abuse control is a separate requirement (rate limits at the function or edge level). When a rate limit rejects a request the caller receives an explicit "try again later" error, never a false "already received".
**4.3 Claims, links and recovery (`link_access_request`, student-access branch only).** The educator branch is unchanged and out of scope.
- **Claim.** The token must belong to an existing `student_access` request; any other token receives one generic refusal. A claim is a row in a new **claims relation**: (request, claiming account, time, state, deciding administrator and time), **unique per (request, account)**. A claim by one account **never blocks or replaces** a claim by another account, so a forwarded or stolen token cannot pre-empt the intended person (the admin screen may collapse the display of several claims, but every claim stays stored and one click away). Replay by the same account is a successful no-op; replay by a claimant whose claim was dismissed leaves it dismissed; and a claim by an account that **is already the link account** (for example the signed-in submitter replaying the token) writes no claim row, because it is already authoritative, so no false "pending" claim is ever shown.
- **A claim is not authoritative (A-I2).** It can grant, close and merge nothing. Claim states: `unconfirmed`, `confirmed_by_email`, `confirmed_by_admin`, `dismissed_by_admin`, `superseded`. Transitions: a claim starts `unconfirmed` (or `confirmed_by_email` at once, 4th bullet below); `unconfirmed` to `confirmed_by_admin` or `dismissed_by_admin` by an administrator action; a `confirmed_*` claim becomes `superseded` when its account stops being the link account; an administrator "link" or "confirm" action on an account sets that account's claim (whatever its prior state, including dismissed) to `confirmed_by_admin`. Nothing else changes a state.
- **Link account.** The request has at most one **authoritative link account**, with a basis (`submitter`, `confirmed_email` or `administrator`), the administrator where applicable, and the time. It is set (i) at submission by a signed-in caller (4.1, basis `submitter`); (ii) automatically, in the same statement as a claim, when the claiming account's **confirmed** email (authentication record, with its confirmation timestamp) equals the request's contact email **and the request has no link account yet** (the claim becomes `confirmed_by_email`); (iii) by an administrator action below. If the request already has a link account different from a later email-matching claimant, nothing is overwritten: the claim stays `unconfirmed` and the request is flagged "two candidates" for the administrator.
- **Administrator actions** (platform admin or super_admin only; each writes a row in `admin_audit_log` with the request, the accounts involved, the previous link account where one is replaced, and an optional reason): **confirm** a claim (it becomes `confirmed_by_admin` and the link account is set); **dismiss** an `unconfirmed` claim ("not this person"; the row is kept, never deleted; **refused with outcome `is_current_link` for the account that is the current link account**, which must first be superseded); **link** the request to a named account with no claim; and **supersede** a link account that has basis `confirmed_email` or `administrator` (replace it). A link with basis `submitter` is the person's own authenticated act and is not superseded in v1: **confirm and link actions that would set a different account on a request that has a `submitter` link are refused** with the outcome `submitter_link_exists`, and the screen tells the administrator that the only allowed action is to dismiss the other claim. A dismissed claim is re-opened only by an administrator, never by the claimant.
- **Effects of supersession and dismissal.** In the same transaction as a supersession, every `confirmed_*` claim of the former link account becomes `superseded`, so no historical state keeps conferring authority. Closures already made by `admin_grant_access` stand: they happened on the link that existed then. Supersession is never retroactive and reverses no grant (reversing a grant is a separate administrator action). After supersession, later closure uses the new link account only. Dismissal changes nothing else.
- **Recovery path for the rightful person after a hostile or mistaken claim.** The rightful account claims with the same token and, if its confirmed email equals the request's contact email, becomes the link account automatically; the earlier claim stays `unconfirmed` and visible to the administrator, who may dismiss it. If the rightful account's email differs from the contact email, the administrator links or confirms it explicitly.
- **`profiles.access_request_ref`.** A pointer set only by that account's own successful claim, written once (the live behaviour), carrying no authority. It is **never changed or cleared** by any administrator action, dismissal or supersession. Code that treats it as an identity match (`AdminDashboard.jsx:1386-1389`) is replaced by the server matching of 4.6.
- **Bounded abuse.** One claim per account per request, and the token is a `uuid` that must be known. A rate limit on claim attempts per account belongs to the abuse-control requirement of 4.2. The admin screen shows the confirmed-email claim first and collapses the others ("3 other claims").
- **Threat model, stated.** A forwarded signup link lets a second account claim. That claim is visible as unconfirmed, cannot grant, close or merge anything (A-I2), does not stop the rightful account from claiming and being confirmed by email, and can be dismissed by an administrator. A confirmed-email match proves control of the mailbox the request named.
**4.4 Authoritative links.** A request has an authoritative link to account X exactly when its link account is X (4.3). A bare requester id on a legacy row, a claim, a typed email and a ref token are not links.
**4.5 Closure (`admin_grant_access`).** In one transaction it grants access, then closes (a) the request the administrator explicitly selected, if any (that selection is itself the confirmation), and (b) every open `student_access` request whose link account is the account being granted. It never closes by email or by a claim. The audit entry lists the closed request ids.
**4.6 Admin screen.** Shows each request as: **linked** (link account and basis); **claimed, awaiting confirmation** (each claimant's name and email beside the request's contact details, with confirm and dismiss actions); **suggested by email** (a profile whose email equals the contact email, not confirmed) with an explicit "link to this account" action recorded with basis `administrator`; **two candidates** (4.3); or **not linked**. A **supersede link** action is offered where 4.3 allows it. All matching and normalization run on the server, not by exact client-side comparison. In User Management, a Tier B row shows the account's course, institution and any linked, claimed or suggested access request.
**4.7 New objects for access requests (design list, no SQL).** On `access_requests`: link account, basis, linking administrator and time; a flag for contact-email difference; a flag for "two candidates"; email normalization on write; the two partial unique indexes and the target-validation trigger of 4.2. A new **claims relation** (request, claiming account, claimed time, state, deciding administrator and time; unique per request and account).
**Read and write contract for the claims relation (A-I11).** The relation has row-level security enabled with **no policies** and no privilege for `anon`, `authenticated` or `PUBLIC` (explicit revoke; default privileges are not relied on). It is written only by SECURITY DEFINER functions. It is read only through two functions, each with explicit EXECUTE grants, an internal authorization check and a pinned `search_path`. Access depends on the caller's **relationship to the request**, of which there are three, not on the role label alone:
- **link account**: the caller is the request's current link account (this includes a `submitter`, who has no claim row);
- **claimant**: the caller has a claim row on the request and is not the current link account;
- **neither**.
| Caller | Administrator reader (`get_request_claims`) | Claimant reader (`get_my_claim_status`) |
|---|---|---|
| Anonymous | no EXECUTE | no EXECUTE |
| Signed in, platform admin or super_admin | allowed; returns, for the request, every claim with claimant name and email, state, deciding administrator and time, and the current link account and basis | applies the rule below to the admin as any other caller |
| Signed in, any other role (student, professor, group admin) | refused | applies the rule below |
**One ordered rule for the claimant reader, evaluated on current authority** (the first matching line decides; the function checks the relationship internally, because the relation's revokes and RLS alone do not provide it):
1. the caller **is the current link account** gives `linked`, whatever any claim row says (submitter with no claim; a confirmed claim before supersession);
2. otherwise the caller has a claim in state `unconfirmed` gives `pending_review`;
3. otherwise (state `dismissed_by_admin`, `superseded`, `confirmed_*` of a former link account, or **no claim at all**) gives **no row**, the same response for all of them and the same as a request that does not exist, so a dismissal or supersession is never disclosed and no other claimant is ever revealed.
Because a dismissal is refused for the current link account (4.3) and a link or confirm action sets the claim to `confirmed_by_admin`, "link account gives `linked`" and "dismissed gives no row" can never both apply to one caller. The earlier phrase "ordinary students get nothing" is withdrawn: an ordinary student who is the link account or an unconfirmed claimant gets the output above; one who is neither gets nothing. Real-role tests: a submitter with no claim (`linked`); a confirmed claim before supersession (`linked`) and after (no row, claim `superseded`); an unconfirmed claim (`pending_review`); a dismissed claim (no row); an attempt to dismiss the current link account (refused `is_current_link`); a dismissed claimant later linked by an administrator (`linked`); an ordinary-student claimant versus an ordinary-student non-claimant; a professor and a group admin in each relationship; anonymous callers; directly and through both functions.

## 5. Invites (batch groups)
- **Invite records** replace the bare token for batches: id, batch, a **UNIQUE** token, an **`is_original`** flag (at most one original invite per batch, the one whose token equals the legacy column token or that was created with the batch), an immutable order value `created_seq` (6.2), label (for example "Inter May 27 – WhatsApp group A", length-limited), created by and when, optional expiry, revoked flag with who and when, and an optional intended recipient (an account, or a verified email). The invite relation is a relation under A-I11 (row-level security, no client policies or direct privileges, access only through the create, list, revoke and join functions, because it holds the tokens). A shared **cohort link** (no recipient) stays the default; recipient-bound invites are an option for known students; single-use links are deferred until a need is confirmed.
- **Migration and the old bearer token (A-I10, A-I11).** Existing shared links must keep working, every batch must always have a working link, and the old token must stop being readable. **Live facts, each from saved live evidence (RUN 6, RUN 1A, F1, F2, G4), not from repo documents:** `study_groups.invite_token` is a **`NOT NULL`** `uuid` with default `gen_random_uuid()` (RUN 6; `DATABASE_SCHEMA.md` calls it nullable and is wrong); `is_batch_group` and `group_type` are **two independent columns** (`group_type` is `NOT NULL`, CHECK `batch`, `system_course` or `custom`, default `custom`), and the live `join_group_by_token` treats a group as a batch if **either** is set (its own comment: "group_type = 'batch' is honoured too (it drifted once, Sprint 8.3)", RUN 1A); `anon` and `authenticated` hold **table-level** SELECT, INSERT, UPDATE, DELETE and TRUNCATE on `study_groups` and `study_group_members` (F1), so a column revoke would deny nothing; `sg_select_member` lets any member read the group row; `sg_insert` checks only `created_by = auth.uid()`; `sg_update_creator` and `sg_delete_creator` constrain `is_batch_group` but **not** `group_type` (F2, RUN 6); there is no trigger on `study_groups` or `study_group_members` (G4); the column **cannot be dropped**, because non-batch groups still use it directly (`GroupDetail.jsx:729,742`) and `join_group_by_token` and `get_group_preview` serve both group types; `create_batch_group` inserts a batch without a token and relies on the column default (repo copy `sprint8.0/02_FUNCTIONS_batch_join_approval.sql:341-358`; the live body is captured by diagnostic 3, run H2). **One definition is used everywhere in this brief: a group is *batch-shaped* if `is_batch_group = true` OR `group_type = 'batch'`**, and every rewritten function, policy, trigger and verification below uses it. "Ignored" is not a security boundary, and `NOT NULL` is preserved, so the real token is **overwritten with a fresh random, unlinked `uuid`** instead of being cleared to NULL. In this order:
  0. *Measure, then close the direct client paths to batch groups, to their members and to the counter, before anything depends on them:* (a) diagnostic 3 run H1 counts the groups by (`is_batch_group`, `group_type`); **if any row has the two markers disagreeing, a separately reviewed data fix makes them agree before (b)**; (b) policies: `sg_insert` WITH CHECK `created_by = auth.uid() AND is_batch_group = false AND group_type <> 'batch'`; `sg_update_creator` USING and WITH CHECK add `group_type <> 'batch'` (so the old and the new row must both be non-batch on both markers); `sg_delete_creator` adds `group_type <> 'batch'`; `sgm_insert_admin` and `sgm_delete` apply only to groups that are **not** batch-shaped, so a client cannot insert or delete the membership rows of a batch group (batch members leave and are removed through `leave_group` and `remove_group_member`; non-batch flows are unchanged); (c) a BEFORE INSERT and UPDATE guard trigger on `study_groups` (**SECURITY INVOKER**) that, when `current_user` is `anon` or `authenticated`, refuses setting either batch marker, refuses an inconsistent pair, forces `order_seq` to its default on insert and refuses any change to `order_seq` or to a batch-shaped row's `invite_token`; inside the SECURITY DEFINER writers `current_user` is the function owner, so the owner path is allowed and **a client cannot forge it** (this replaces the earlier custom-setting marker, which is not authorization); (d) revoke `TRUNCATE` and any other privilege not needed from `anon` and `authenticated` on `study_groups` and `study_group_members`. Batch groups are then created only by the protected `create_batch_group`. ## 6. Membership states, history and authorization (batch groups only)
**6.1 States.** `invited`, `requested`, `active`, `closed` (existing) plus `rejected`, `removed` and `left` (new). **In v1 no batch writer creates an `invited` row**: a recipient-bound invite lives in the invite relation (5), so a student is never left `invited` by an expired or revoked link (the status stays valid for non-batch groups and for any existing row). `UNIQUE (group_id, user_id)` stays: one row per student and batch is the **current state**, with a **`last_inactive_seq`** order value (and a display time `last_inactive_at`) set by every negative transition (6.2 precedence rule); history lives in an append-only events relation.

**Invite precedence after a negative decision (A-I6).** A recipient-bound invite is reusable in v1 (single-use is deferred), so an **older** invite must never silently reverse a later rejection, removal, leave or closure. The comparison uses an **order value assigned under the shared serialization point, not a clock**: a transaction timestamp (`now()`, `transaction_timestamp()`) is fixed when a transaction **starts**, so a removal that starts first but acquires the lock last would carry an earlier time than an invite created in between, and the old invite would wrongly look newer. Each batch therefore has a **monotonic counter `order_seq`** on its `study_groups` row, incremented only while that **batch row lock is held**. (1) `create_batch_invite`, the batch-creation path and the backfill take the batch lock, increment the counter and store the result as the invite's immutable **`created_seq`**. (2) Every negative transition (reject, remove, leave, archive-close) already takes the batch lock; the **stamping trigger of section 5 step 1** then increments the counter and stores the result as **`last_inactive_seq`** on each membership row that enters a negative status, **overwriting any value a writer or a direct statement supplied** (archive-close gives each row it closes its own fresh value, all later than any earlier invite). (3) `join_group_by_token`, which takes invite, then batch, then membership rows, reads both values under the batch lock: invite `created_seq` **greater than** the row's `last_inactive_seq` (an explicit later re-invite) gives transition 3, `active`; otherwise (an older invite, or a cohort invite) gives transition 7 or 11, a fresh `requested` row for review, with the generic message of 6.5. A student with no row is unaffected. Because every value comes from one counter incremented under one lock, the order of the values **is** the serialized order, whatever order the transactions started or committed in. Timestamps (`created_at`, `last_inactive_at`) stay for display and audit only and are never compared. Expiry is separate and is decided by the timestamp comparison of section 5. Tests: **stagger the transaction start order independently of the lock and commit order** (a removal or rejection that starts first but takes the batch lock after a later-started invite creation has committed must make that invite old, so reuse gives `requested`); the reverse (invite created after the negative transition serialized gives `active`); remove or reject then the same older invite; leave then an older invite; archive-closed then an older invite after restore; both commit orders of remove versus join and of reject versus join; and a catalog test that `order_seq` is changed only inside functions that hold the batch lock.
**Eligibility (A-I7).** The eligibility function of section 7 is invoked at transitions **1, 3, 4, 6, 7 and 11**, that is, wherever a request is created or a student becomes `active`, whichever function performs it (join, including activation through a recipient-bound invite; approve single or bulk; add single or bulk). Transition 2 is not used in v1. Transition 13 (staff using a link) uses the staff variant of section 7. A refusal writes no event and returns the outcome `ineligible`. Transitions 5, 8, 9, 10 and 12 end or preserve membership and are not gated by eligibility.
**Actor kinds:** `self`, `admin` (platform admin or super_admin), `group_admin`, `system` (backfills, migrations, automation). `actor_id` is NULL only for `system`.
**6.3 Events relation (new, append-only).** One row per event: batch, user, event kind, actor kind, actor id, actor role at the time, optional reason (length-limited), the invite id when the event is a request, and a timestamp. Rows are inserted only by SECURITY DEFINER functions in the same transaction as the state change; no client role may update or delete them (the same immutability trigger pattern as `admin_audit_log`, RUN 4). Row-level security is enabled with **no client policies and no direct client privileges** (A-I11).
**6.4 Who can read events (least privilege), through SECURITY DEFINER read functions only.**
- the affected student: their own events; event kind, time and batch name only (no actor, reason or invite label);
- platform admin and super_admin: all fields for any batch;
- an active group admin member of that batch: all fields for that batch, with the actor shown by kind not identity;
- an assigned professor: nothing (roster view only, per 8.8.5d);
- everyone else: nothing.
**6.5 Re-request after rejection or removal.** The server creates a fresh request, writes `reopened_request`, and the admin queue shows a history summary ("previously rejected 12/09; removed 20/09"). A rejected or removed student sees a plain message on the join page. A recipient-bound invite issued **before** the negative event is treated like a cohort link here (it gives `requested`, never `active`; precedence rule in 6.2). Whether a cooldown applies is decision D7.
**6.6 Writers and lock order.** Writers: `join_group_by_token`, `approve_batch_join_request`, `reject_batch_join_request`, `admin_bulk_resolve_batch_requests`, `enroll_user_in_batch_group`, `remove_group_member`, `leave_group`, `archive_batch_group`, `restore_batch_group`, and the invite create, list and revoke functions. Today (RUN 1A, repo): join, approve, reject, bulk resolve, enroll, archive and restore take the batch row lock; **`remove_group_member` and `leave_group` take no lock**. Every revised writer **will** take the same lock order, skipping any step that does not apply to it: **invite row(s), where the writer touches an invite, in ascending id order; then batch row(s) in ascending id order (bulk resolve already does this, RUN 1A); then membership rows in ascending id order; then the events insert**, each state change and its event in one transaction. The deadlock test matrix is derived per writer from the steps that apply to it, and includes every pair of writers that can touch the same invite, batch or membership row.
**6.7 Readers.** A preserved `rejected`, `removed`, `left` or `closed` row must never grant anything. **VERIFIED live policies that ignore membership `status` (F2):** `sg_select_member` (any membership row lets the user read the `study_groups` row; `anon` and `authenticated` hold column SELECT on `invite_token`, F1, so the token is readable by any member), `cgs_select_member`, and the write policies `sgm_delete`, `sgm_insert_admin` and `cgs_delete_own_or_admin`, which test a membership `role = 'admin'` without testing `status`. `sgm_select_own` returns only the caller's own rows. Readers that do test `active`: the group-share branches of `get_browsable_*` and `get_my_batch_groups` (F3B). Every reader and every such policy must be changed so that only `active` confers access, and no stale row exposes an invite token.
**6.8 Privileges (VERIFIED direct write paths, F1 and F2).** `authenticated` (and `anon`) hold table INSERT, UPDATE, DELETE and TRUNCATE on `study_group_members` and `study_groups`; the effective row rules come from policies: `sgm_insert_admin` lets a member with membership role `admin` insert membership rows for **any** user, with any status, into their non-archived group, and `sgm_delete` lets a user delete their own row or a group admin delete any row of their group. Both bypass `remove_group_member`, `leave_group`, eligibility and events. There is no UPDATE policy on `study_group_members`, so the column grants on `status` and `role` have no effect today. The app's only direct write is cancelling an invite (`GroupDetail.jsx:290`, delete where status is `invited`). The SQL gate must make the functions the only write path for batch groups: revoke client INSERT, UPDATE, DELETE and TRUNCATE on `study_group_members`, move the invite cancel to a function, and retest direct writes as a real `authenticated` caller; non-batch study groups are outside this brief but share the table, so the change must keep their flows working (to be listed in the SQL plan). **The same applies to `study_groups` itself** (F1, F2, G4): the live `sg_insert` policy lets a signed-in user insert a batch-shaped row directly, there is no trigger, and TRUNCATE is granted; section 5 step 0 closes that path first (policy, counter guard trigger, TRUNCATE revoke, real-role tests), because the invite and order-counter design depends on batch groups being created only by the protected writer.

## 7. Eligibility and the Tier B question
One server function, **eligibility(student, batch)**, is the only place the rule lives (A-I7). It is invoked at every transition marked in 6.2 (1, 3, 4, 6, 7, 11), from `join_group_by_token` (including activation through a recipient-bound invite), single and bulk approve, `enroll_user_in_batch_group` (single and bulk Add) and the reopen path. It refuses when:
- the profile is not a student (the staff variant for transition 13 requires platform admin or super_admin and applies none of the student rules below);
- the profile status is suspended (VERIFIED: no live join, approve or enroll function checks it, RUN 1A and follow-up F4; no policy mentions it; latent today because all 263 profiles are `active`, F7);
- the batch is archived;
- the access rule of decision D4 fails. As recommended, D4 allows a Tier B student (so this adds no refusal, only the banner of section 9).
It is evaluated **again at the moment of approval or activation**, not only when the request was made, because the profile can change in between: a student suspended after requesting is refused at approval with the outcome `ineligible`, the request stays `requested`, and only the administrator sees the reason code. Bulk operations return a per-row outcome. The student sees the generic refusal of section 5 and learns no reason. Batch membership never grants content entitlement (A-I7). Today the rules differ: bulk Add refuses Tier B students, single Add shows no picker for them, approve and join check no profile status (matrix rows 4, 6, 11).

## 8. Content access model (principles; implementation is a later epic)
No payment is taken in the app in v1 (A-I9): a manual grant reads "creator-granted" or "externally fulfilled", never "paid", unless a real transaction is recorded. Keep as independent concepts, never one flag: **provenance** (official ICAI versus creator material; `content_creators` exists only for revenue-share attribution today, `DATABASE_SCHEMA.md:72,241`); **access policy** per item (`free`, `private`, `preview`, `restricted`; official material always `free`); **entitlement** (who, from whom, why, until when, revoked or not; origin one of creator direct, batch rule, delegate, promotion, externally fulfilled); batch membership; My Study enrollment; authorship. A batch grants content only through an explicit entitlement rule. Admin override is an audited emergency action. Enforcement must be in RLS and `get_browsable_*` together, not only in screens. `account_type` stays as the platform "full content access" flag during the transition (240 enrolled, 16 Tier B students, RUN 7); the entitlement model starts empty and existing grants are migrated by a separate reviewed step.
