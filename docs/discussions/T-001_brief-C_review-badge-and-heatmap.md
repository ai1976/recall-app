## 1. What the Founder sees today, in plain words
1. **The red Review badge does not update** after you Pause, Resume, Remove or Re-add a card, finish a review, or switch course; it is only correct after a full reload. (After Pause or Remove the number should fall; after Resume or Re-add it may rise. The defect is that it does not change at all.)

## 4. Design (PROPOSAL)
### Point 6: one meaning of "due", and a badge that stays correct
**C-6.1 The shared eligibility rule (one definition).** A card counts as "due-eligible" for a student when **all** hold, evaluated against `v_today`, the student's local date from `profiles.timezone`: (a) `reviews.status = 'active'`; (b) `skip_until IS NULL OR skip_until <= v_today`; (c) not a `concept_card`; (d) the course rule of the live predicate; (e) the visibility rule of the live predicate; (f) **new:** an **active** `my_cards_enrollment` row for the card (the exact boundary of `get_my_cards`). The student's "due" counts are all taken from this one set.

**C-6.2 The day-zero invariant and the future-bucket contract (separate).**
- **Day zero (badge, Progress "due today", the Dashboard zero-state strip):** the count equals the number of cards the Review page lets the student review today, `|get_study_queue ∩ get_my_cards|`, and equals `get_due_forecast.due_today` and bucket 0 of `get_due_forecast_buckets`. This is an equality, tested for **every profile** (C-6.5).
- **Future buckets (Forward Load) and `due_next_7` / `due_next_30`:** they describe the *same eligible set* spread by scheduled date; they are **not** "what Review permits today". The skip boundary (b) is **kept exactly as live, evaluated against `v_today` for every bucket** (a card whose `skip_until` is still in the future is excluded from every bucket, including buckets dated after its skip date; the live behaviour, preserved on purpose, a known simplification that is not a full workload forecast and is not changed by this brief). Invariants: for every profile, the sum of all eight buckets equals the number of eligible cards **with a non-null `next_review_date`**; `due_next_7` and `due_next_30` equal the count of that set with `next_review_date <= v_today + 7` and `+ 30`; bucket 0 equals `due_today`.
- **Null `next_review_date` (DEFINED in v6; evidence: C-00, `docs/discussions/evidence/T-001_C00-*`, diagnostic 09 v4 `22f8db788c4f`, run 07/10/2026).** **VERIFIED live:** `reviews.next_review_date` is a nullable `date` with no default; **671 of 8,461 rows are null (590 `active`, 81 `suspended`, none `mastered`), all ordinary flashcards, held by 14 users, created between 02/01/2026 and 19/01/2026, all with a last-reviewed time**; `reviews` is a plain unpartitioned table with two AFTER triggers that never write it and no rules. **VERIFIED in saved RUN 1B:** the Review page's `get_study_queue` requires `next_review_date <= v_today`, so it never offers a null row; the live cumulative forecast never counts it; the live bucket `CASE` puts it in bucket 7. **Definition (PROPOSAL):** a review whose `next_review_date` is null is **not due and is excluded from every figure and every bucket**, in the badge, the Progress tile, the Dashboard strip and Forward Load, exactly as the Review page treats it. The invariants above hold with "non-null" now the rule, not a caveat. **Visible effect, stated:** Forward Load's last bucket will show up to 590 fewer items for 14 students; this is a correction of a number that no Review session could ever clear. **Not decided here and not repaired:** why these rows have no date (OPEN) and whether the 590 active rows should be given a date by a one-off reviewed data fix (Founder decision D-C5, below); the mandatory null-date TEST case of C-6.5 item 3 asserts the definition.

**C-6.3 One shared implementation boundary, with an access-control contract, and a parity test.**
- One internal helper (name and exact form fixed at the SQL stage) holds the C-6.1 rule; **both** `get_due_forecast` and `get_due_forecast_buckets` read from it, so they cannot drift from each other. The Review page's composition (`get_study_queue` ∩ `get_my_cards`) is **not** changed; an all-profile parity test (C-6.5) compares it with the helper.
- **Access-control invariants for the helper (QA Round 72 blocking 2).** (1) It is **not executable by `PUBLIC`, `anon`, `authenticated` or `service_role`** (explicit REVOKE, then no grant to application roles); only the two public RPCs, which are `SECURITY DEFINER` and keep their own caller-is-target-or-`is_admin()` guard, reach it through their owner; (2) a pinned `search_path` (`public, extensions`, as the live functions); (3) it takes the target user id and date as parameters and returns only the eligible set for that user, never a list across users; (4) its exact ACL is asserted from the catalog and the **direct invocation is tested as `authenticated` (own id and another user's id), as an administrator and as `anon`: each must fail with a permission error**; (5) the two public RPCs' grant ceiling (`authenticated`, `postgres`, `service_role`) is unchanged and re-asserted.

**C-6.4 The refresh contract (one behaviour, one place).**
- *Every mutation path emits one signal (QA Round 72 blocking 1).* A single small module (for example `src/lib/dueSet.js`, name fixed at build time) exports **thin wrappers for every mutating call in P6-E5**: `applyReview`, `skipCard`, `suspendCard`, `unsuspendCard`, `resetCard`, **`skipTopicCards`, `suspendTopicCards`**, `addToMyCards`, `removeFromMyCards`, `bulkPauseMyCards`, `bulkResumeMyCards`, `bulkRemoveFromMyCards`, **`updateProfileDueFields` (one wrapper for every update-time write of `course_level` or `timezone`, with or without the other profile fields in the same update)**, and, from QA Round 76, **`acceptFriendship`, `removeFriendship`, `deleteFlashcard`, `deleteFlashcards` and `deleteNote`** (each performs the existing delete or update and notifies only on success; `deleteNote` notifies because its linked cards go with it). Each wrapper calls the RPC (or update) and, **only on success**, calls `notifyReviewDataChanged()`; **all call sites listed in P6-E5 switch to the wrappers**: `StudyMode.jsx` (grade, skip, suspend, reset, **snooze topic, pause topic**), `Progress.jsx` (resume), `MyCards.jsx` (single and bulk Pause, Resume, Remove, Re-add), `PracticeMode.jsx` (add to My Cards), `FriendRequests.jsx` and `NotificationCenter.jsx` (accept), `MyFriends.jsx` (unfriend), `MyFlashcards.jsx`, `NoteDetail.jsx` and `MyNotes.jsx` (the four delete paths), and the four profile writers: `CourseContext.jsx` (course switch), **`Dashboard.jsx` (profile-completion modal), `ProfileSettings.jsx` (profile save) and `AuthContext.jsx` (time-zone sync, which notifies only when it actually changed the stored value)**. A bulk wrapper notifies **once after its last chunk finishes**, and also when it stops part-way after at least one chunk succeeded. The enforcement is **classification-based and fail-closed** (QA Round 76 blocking 2; an enumeration alone can never prove completeness, so the guarantee is that **no data-changing call can enter the code unclassified**): **(1) a reviewed classification manifest** (a file in the repository, name fixed at build time) lists **every** direct `.rpc(...)` call and **every** `.from(table).insert / update / upsert / delete` call in `src`, one entry per call site, each marked `due-changing` (must go through a wrapper of this module) or `not due-changing` with a one-line reason that names the C-6.1 inputs it does not touch (review state, enrollment, suspension, skip date, friendship, card existence, course, time zone); **(2) a syntax-aware lint rule that fails the build** on any such call that is not in the manifest, on any `.rpc(...)` whose name is not a string literal and is not an allowlisted map inside the wrapper module, and on any `.from('profiles').update(...)` whose payload cannot be resolved to literal keys (**fail-closed**: an unresolved, spread or variable-held payload outside the wrapper module is rejected); a **new** literal-named call, due-changing or not, therefore cannot be merged until a reviewer has classified it; **(3) the enumerated wrapper tests** of C-6.5 item 5, one per wrapper; **(4) a separate drift check** that every RPC name in the manifest exists in the live function catalogue (it detects a removed or renamed function; it does **not** detect an unlisted one, which is layer 2's job). The flashcard and note updates that already exist in `MyFlashcards.jsx`, `NoteEdit.jsx`, `FlashcardCreate.jsx` and the other files found by the search are classified at build time, against the C-6.1 rule, in the manifest review; any that touches the course, subject or visibility of a card that the C-6.1 rule reads is `due-changing`. The lint and manifest are a guard against omission, not a proof of behaviour; the wrapper tests prove the behaviour.
- *Debounce and visibility.* A graded answer notifies with a trailing delay of 1.5 seconds so rapid answers coalesce into one refetch, plus once when the review session ends or the page is left; the tab becoming visible again after more than 60 seconds also notifies (review activity on another device), **and so does entering the Dashboard, Progress or Review page when the snapshot is more than 60 seconds old** (the stale-response rule of the snapshot applies). No polling.
- *One published snapshot (QA Round 72 blocking 4).* The nav context fetches `get_due_forecast` and `get_due_forecast_buckets` **together** and publishes `{dueToday, dueNext7, dueNext30, buckets}` as **one snapshot**: both responses are staged; the snapshot is published **only after both succeed**; each refresh carries an increasing request number and **a response that is not from the latest request is discarded** (out-of-order or overlapping refreshes cannot publish an older snapshot); if either request fails the **previous snapshot is kept** and an error state is set (a later successful refresh clears it).
- *Single source in the app.* The nav badge, the Progress "due today" tile, the Dashboard Forward Load chart and the Dashboard zero-state strip **read the snapshot from that context** and stop running their own due queries (the Dashboard's `get_study_queue` call for `reviewsDue` and the Progress and Forward Load calls are removed; the strip shows when the snapshot's `dueToday` is 0). The Review page's queue logic is unchanged.

### Point 7: an honest, accessible heatmap
**C-7.1 The data contract (new RPC; the old one stays until the frontend is verified).** Returns, per local date: `review_count` (computed exactly as the live function does, apart from the window of C-7.3), `in_app_seconds` (`study_mode` plus `practice_mode`), `offline_seconds` (`manual`), `study_seconds` (the total over **all** sources), and `other_seconds` = `study_seconds − in_app_seconds − offline_seconds`, which must be 0 for every day (so a source outside the three known ones fails a test instead of disappearing).
**C-7.2 Authorization and grants (preserved, not widened).** Caller must be the target or `is_admin()`, exactly as the live function (P7-E1): `SECURITY DEFINER`, the same pinned `search_path`, `anon` refused, grants no wider than the live function's (RUN 2). If the Founder wants administrator access removed, that is a separate decision (D-C4, recommended: keep as live).
**C-7.3 Day and window contract (an intended change at the window edge).** (a) Review days: grouped by the profile timezone date, as live. (b) Study days: `session_date` as written by the client; not re-derived. (c) **The window is the dates from (student's local today − `p_days`) up to the student's local today, for all three sources,** replacing the live mix of `NOW()` and the server's `CURRENT_DATE`. Because that is intentionally different from the old boundaries, **the first included day, and at the far end the last, can differ from the old function for users away from the server's date; this is the one intended difference** (see C-7.5). (d) The known limit that a student whose device date differs from their profile timezone can see a one-day difference between review days and study days is recorded and not changed here.
**C-7.4 Frontend contract.** Dates from the server are calendar-date strings (`YYYY-MM-DD`); the component never calls `new Date('YYYY-MM-DD')` (UTC) and never `toISOString()`: it splits the string into year, month and day and builds a local date, or keeps the string as the cell key; the grid is built from local dates with `toLocaleDateString('en-CA')`. Each cell is a focusable control with an accessible name (date, in-app, offline, total, reviews; not colour alone); pointer hover and keyboard focus show a concise card (date, in-app time, offline time, total, reviews); tap, Enter or Space **pins** the detail, which closes on Escape, a second tap or focus loss; the native `title` is removed; reduced-motion is respected; the existing visual language is kept.
**C-7.5 Proof for point 7 (read-only reconciliation over all profiles, plus real-role TEST). The old-versus-new comparison is restricted so that it cannot contradict C-7.3 (QA Round 72 blocking 3).**
1. **Primary reconciliation, every profile and every day: the new function equals an independent recomputation from the source rows under the C-7.3 window rule** (`reviews`, `user_activity_log`, `study_sessions`), for `review_count` and each of `in_app_seconds`, `offline_seconds`, `study_seconds`, with `other_seconds = 0`.
2. **Old-versus-new, only on the common date set, defined as the full local calendar days wholly inside both windows** (the old review cutoff is an instant, `NOW() - p_days`, so its first calendar day is only partly included and is **not** in the common set): for every profile, on those days, `review_count` and `study_seconds` are **equal**.
3. **The boundary delta is exactly accounted for:** for every profile, the difference between the new and old results on the dates in the symmetric difference of the two windows (the first and last day, in the profile's own time zone) equals **exactly** the source rows dated in that difference, computed by the test from the source tables **with the exact timestamp and date predicates of both windows (not by assuming the difference is whole dated rows)**, and nothing else.
4. **Authorization:** own rows allowed; **another student's read refused, an administrator's read allowed, `anon` refused.**
5. **Boundary cases:** a study-only day, a review-only day, an empty day, a day with all three sources, a user at +14 and at −12 on the window edge, a user whose profile time zone differs from the server's date.
6. **Frontend:** keyboard-only walk-through; screen-reader name of each cell; **pointer hover, touch tap, pin, close by Escape, by second tap and by focus loss; reduced-motion respected;** a negative-UTC browser time zone; no `toISOString()` or UTC string parsing left in the component.
**C-7.6 Not here.** Course and subject in a day-detail view (brief B C4), in-app session classification, professor views (totals only, unchanged).
