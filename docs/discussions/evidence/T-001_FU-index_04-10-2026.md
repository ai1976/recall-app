## Claude's reading (analysis, NOT evidence; recorded here so it is not lost; the thread round will carry the audited version)
Facts below are quoted from the files; labelled VERIFIED when a file shows it, OPEN when it does not.

**Brief A**
1. **Tier B lock is not enforced in the database (VERIFIED, F4 and F2).** No policy mentions `account_type`; only four functions do (`admin_bulk_add_to_batch`, `admin_grant_access`, `fn_create_profile_on_signup`, `fn_guard_profiles_protected_columns`). `get_browsable_notes` and `get_browsable_decks` (F3B) gate by visibility, group share and course text, never by `account_type`. Public notes and flashcards are readable under the `public` policies (F2).
2. **No join, approve or enroll function checks a suspended profile (VERIFIED, F4):** only `admin_bulk_add_to_batch`, `batch_group_access_denial` and `get_my_batch_groups` among batch functions mention `suspended`. No policy mentions it. Today this is latent: all 263 profiles are `active` (F7).
3. **Direct table paths exist (VERIFIED, F1 and F2).** `authenticated` holds INSERT, UPDATE, DELETE, TRUNCATE on `study_group_members`, `study_groups`, `access_requests`, `flashcards`, `notes`, `flashcard_decks`, `content_group_shares`; `anon` holds the same table privileges. RLS is enabled on every public table, so rows are governed by policies, but:
   - `sgm_insert_admin` lets a member whose membership `role = 'admin'` insert membership rows for any user into their (non-archived) group, with any status; `sgm_delete` lets a user delete their own row or a group admin delete any row of their group. These bypass `remove_group_member`, `leave_group` and any eligibility rule. The app itself uses direct delete only to cancel an invite (`GroupDetail.jsx:290`).
   - `Authenticated users can submit access requests` allows a direct INSERT with `requester_user_id = auth.uid()` and no other column check, bypassing `submit_access_request`.
   - **TRUNCATE is granted** to `authenticated` and `anon` on those tables (it bypasses RLS); PostgREST does not expose TRUNCATE, so whether this is reachable depends on other connection paths (OPEN).
4. **Policies that ignore membership `status` (VERIFIED, F2):** `sg_select_member` (so any membership row exposes the group row including `invite_token`, a column `anon` and `authenticated` hold SELECT on, F1), `cgs_select_member`, `cgs_delete_own_or_admin`, `sgm_delete`, `sgm_insert_admin` (role `admin` without status). All must be revisited before preserved `rejected`/`removed`/`left`/`closed` rows exist. Reads that do check `active`: the group-share branches inside `get_browsable_*`, `get_my_batch_groups`.
5. **`profiles` columns `role`, `account_type`, `status`, `access_request_ref` carry UPDATE grants for `authenticated`** (F1) under an own-row policy; the repo's `docs/database/security/19_SCHEMA_profiles_protected_columns_guard.sql` blocks changes by a trigger (function `fn_guard_profiles_protected_columns` exists, F4; that the trigger is attached live is OPEN). `profiles.email` is not selectable by clients (F1).
6. **Access requests today (F8):** 6 requests: 5 `student_access`, all open, all item-level (3 notes, 2 decks, none platform-level, none malformed, none with a missing item), 1 `institute_inquiry`. Requester id present on 3, absent on 2. No duplicate groups of any kind. No contact email differs from a profile email; none of the 2 id-less requests matches a profile email. So the legacy cleanup precondition does not arise today, and the platform-level index case has no existing rows.
7. **Invites (F7):** 16 study groups, 0 duplicate `invite_token`. Memberships: batch active 260 students + 4 professors + 1 admin; batch `requested` 4 students; non-batch active 35 students; non-batch `invited` 3 students. There are 0 `invited` rows in batch groups, matching RUN 6.
