## 3. Claude's reading (analysis, NOT evidence; for QA to audit)
- **Cascade closure.** Deleting a user (an `auth.users` row, which cascades to `public.profiles`) reaches **40 tables** by `ON DELETE CASCADE` (2 roots, 33 at depth 1, 5 at depth 2). Edges: 70 in all: 49 CASCADE, 20 SET NULL, 1 NO ACTION. The only NO ACTION edge is `public.flashcard_batch_provenance.created_by -> profiles`, matching the comment in `admin_delete_user_data` that it is the only foreign key with no delete rule (it detaches that column first). The group tables are reached: `study_groups` (via `created_by`), `study_group_members`, `content_group_shares` and `batch_group_professors` at depth 1, `batch_group_archives` at depth 2. **So deleting a profile cascades to every group that user created, batch groups included, and to their memberships, shares, archives and professor assignments.** SET NULL edges into the group tables: `study_group_members.invited_by`, `study_groups.archived_by`, `batch_group_archives.archived_by`, `batch_group_professors.assigned_by`.
- **Triggers.** 34 user triggers on 12 tables (all enabled), 30 trigger functions, all plpgsql, 19 of them SECURITY DEFINER; **no rewrite rule**; **none on any group table**. Eight triggers fire on DELETE: the audit-log append-only guard, the counters on `flashcards`, `friendships`, `notes`, `reviews` and `upvotes`, and `trigger_update_deck_card_count`; 17 more fire on UPDATE only. The trigger definitions (P3) and the extra closure definitions (P8) **do not mention** `study_group*`, `content_group_shares`, `batch_group*`, `access_requests` or `invite_token`. `fn_guard_admin_audit_log_immutable` is a working example of a guard that blocks direct deletes and edits but lets the foreign-key SET NULL through (its UPDATE branch allows only `admin_id` and `target_user_id` going to NULL), so profile erasure works with that guard today.
