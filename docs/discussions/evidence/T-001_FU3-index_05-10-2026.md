## Claude's reading (analysis, NOT evidence; the thread round will carry the audited version)
Facts are quoted from the files; OPEN where the files do not show it.

**H1: the two batch markers never disagree.** 16 groups: 9 `system_course` with `is_batch_group = false`; 3 active `batch` with `is_batch_group = true`; 2 archived `batch` with `is_batch_group = true`; 2 `custom` with `is_batch_group = false`. There is no row with `group_type = 'batch'` and `is_batch_group = false` or the reverse, so **no marker-repair data fix is needed before step 0** of brief A. The step 0 policies and guard still close the path for future rows.

**H2: live bodies (all four SECURITY DEFINER, `search_path` set).**
- `create_batch_group` is as the repo copy said: it checks `is_admin()` and inserts `is_batch_group = true`, `group_type = 'batch'` with **no token** (the column default supplies it) and returns the id. It sets **both** markers.
- `archive_batch_group` checks `is_admin()`, locks the group row with `FOR UPDATE` (so it takes the batch lock before touching memberships), requires `is_batch_group` (it does **not** look at `group_type`), writes a `batch_group_archives` row, sets `archived_at` and `archived_by`, and sets memberships with status `requested` or `invited` to `closed` with `closed_at` and `closed_reason = 'batch_archived'`. Active rows are unchanged.
- `restore_batch_group` checks `is_admin()`, locks the group row `FOR UPDATE`, requires `is_batch_group`, clears `archived_at` and `archived_by`, and **does not touch memberships** (closed rows stay closed).
- `get_study_time_stats` raises "Access denied" unless `p_user_id` equals `auth.uid()` or the caller is an admin; a non-NULL target id other than the caller's is refused. **Corrected after QA Round 44:** the guard uses `IS DISTINCT FROM`, so an anonymous call with a NULL target id passes the guard and returns zero-valued aggregates (no user data); the `anon`-executable ACL (G2) is therefore a minor information-free exposure, not a data leak, and not a lead for the group design.
- Consequence for the SQL: the rewritten `archive_batch_group` and `restore_batch_group` must use the batch-shaped definition of brief A (either marker), not `is_batch_group` alone; the existing lock order (group row first) already matches brief A 6.6; the existing `closed_at` and `closed_reason` columns are reused.

**H3: trigger definitions (32 triggers, all enabled).** There are **no triggers** on `study_groups`, `study_group_members`, `access_requests`, `disciplines`, `subjects`, `study_sessions` or `topics`. On `profiles`: `trg_badge_new_profile` (AFTER INSERT); `trg_course_change_archive_restore` (**AFTER UPDATE OF `course_level`**, `WHEN old.course_level IS DISTINCT FROM new.course_level`); `trg_guard_profiles_protected_columns` (**BEFORE UPDATE**, `WHEN` any of `id`, `role`, `account_type`, `status`, `email`, `access_request_ref` changes; it does not fire for `course_level` alone). So a new BEFORE trigger on `profiles.course_level` (brief B 5.3a) runs independently of the guard, and its rewrite is seen by the AFTER archive-restore trigger (whose `WHEN` is evaluated on the final row), as brief B requires. On `flashcards` and `notes` there are BEFORE guard triggers (`trg_guard_flashcards_is_verified`, `trg_guard_notes_privileged_columns`, `trg_require_note_provenance`, `trg_guard_flashcard_batch_move`); a new guard for brief B 6.3 must coexist with them and its name decides its firing order among BEFORE triggers (alphabetical). `admin_audit_log` is made immutable by **two triggers**, a row trigger (BEFORE DELETE OR UPDATE) and a statement trigger **BEFORE TRUNCATE**, which is a pattern the events and invite relations can reuse, and shows that TRUNCATE can be blocked by a trigger as well as by a privilege revoke.

**H4: policies on the course catalogue tables.** `disciplines`: SELECT for signed-in users and **INSERT for admins only** (`is_admin()`); **no UPDATE or DELETE policy**, so a client cannot rename or delete a discipline today (RLS is enabled, F2), although `UPDATE`, `DELETE` and `TRUNCATE` privileges are granted (G4); TRUNCATE bypasses RLS and remains the exposure. `subjects` and `topics`: **only a SELECT policy**; there is **no INSERT, UPDATE or DELETE policy**, so with RLS enabled a browser write to these two tables is refused for every non-bypass role. That means the admin page `BulkUploadTopics.jsx`, which inserts and updates subjects and inserts topics from the browser, would currently be refused by the database for those writes (its `disciplines` insert by an admin is allowed). Whether the page is in use, or how subjects and topics are actually created today, is OPEN and should be tested as a real admin before any privilege change.
