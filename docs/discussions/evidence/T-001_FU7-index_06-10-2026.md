## 3. Claude's reading (analysis, NOT evidence; for QA to audit)
- **No application client role can reach the `cron` schema (one trusted operational exception, `cli_login_postgres`, is stated at the end of this paragraph; corrected after QA Round 70).** Schema `cron` is owned by `supabase_admin`; the ACL grants USAGE to `postgres` (with grant option) and USAGE and CREATE to `supabase_admin`, nothing to PUBLIC. Effective USAGE: `postgres`, `supabase_admin` (superuser), `supabase_etl_admin` and `supabase_read_only_user`; effective CREATE: `supabase_admin` only. **`anon`, `authenticated`, `authenticator`, `service_role`, `dashboard_user` and `cli_login_postgres` have neither USAGE nor CREATE.** So the PUBLIC EXECUTE on `cron.schedule` (two forms) and `cron.unschedule` (two forms), the question raised from diagnostic 5, is not reachable by a schema-qualified call from those roles: it answers Round 61 C2 for the six roles measured. The saved role graph (FU4 J1) shows no client role is a member of, or can SET ROLE to, `supabase_etl_admin` or `supabase_read_only_user`, the two other roles with effective USAGE. **Correction (QA Round 70, non-blocking 1): the sentence "no client role can reach the cron schema" was too broad.** `cli_login_postgres` has no direct USAGE, but C5 shows it can SET ROLE to `postgres`, which has effective USAGE, so it **can** reach the schema, and the routines executable by PUBLIC, through that role transition. It is a trusted operational role (the Supabase CLI login), not an application client. The evidence supports no such path for `anon`, `authenticated`, `authenticator`, `service_role` or `dashboard_user`. Planning must keep the `cli_login_postgres` to `postgres` path explicit; it is already in the plan's trusted set.
- **Job tables.** `cron.job` and `cron.job_run_details` have row-level security enabled (not forced), owned by `supabase_admin`, with one policy each for ALL commands: `username = CURRENT_USER`; SELECT is granted widely and `job_run_details` DELETE too, but both sit behind schema USAGE and the row policy. The two sequences (`jobid_seq`, `runid_seq`) are owned by `supabase_admin` with default ACLs: USAGE and UPDATE only `supabase_admin`, SELECT `postgres`, `supabase_admin`, `supabase_etl_admin`, `supabase_read_only_user`.
- **Jobs.** Two active jobs, both in database `postgres`, both run as `postgres` (a role with BYPASSRLS and CREATEROLE). Neither mentions the protected group objects, the `cron` schema, dynamic SQL, or any DML or DDL word; the only non-system routine name occurring in either is `net.http_post` (one overload). Commands are 263 and 291 characters; their full SHA-256 values are saved for later equality checks (command text never returned). **R1 matched neither job** because `first_word` is null for both: the command probably starts with a character other than a letter (for example a newline, which `btrim` does not remove), so both are "requiring review" by construction; this is the rule failing closed on a formatting detail, not a finding about the jobs, and no change is proposed for a file that has run.

This matches FU4 J1 and the plan's C2 trusted set `{postgres, cli_login_postgres}`.
