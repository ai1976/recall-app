**J1 (saved): roles and the migration identity.**
- The SQL Editor runs as `postgres` (session and current user). `postgres` is **not a superuser** but has CREATEROLE, CREATEDB, REPLICATION and **BYPASSRLS**; the only superuser is `supabase_admin`.
- `postgres` holds ADMIN, SET and INHERIT on `anon`, `authenticated`, `authenticator` and `service_role` (granted by `supabase_admin`). So `postgres` can create `grp_batch_writer`, and grant it.
- **New fact for C2:** the login role `cli_login_postgres` (NOINHERIT) can `SET ROLE postgres` (edge `cli_login_postgres` to `postgres`, set only), so by the server's own closure it can also reach everything `postgres` can reach, including a future `grp_batch_writer` grant to `postgres`. Plan v5 C2 item 3 says that for every role other than the trusted identity and superusers all three `pg_has_role` answers must be false; **as written it would fail on `cli_login_postgres`** unless the trusted set is defined as {`postgres`, and `cli_login_postgres` as the identity's own CLI login}. It needs an explicit decision.
- Other roles with CREATEROLE: `dashboard_user`, `supabase_auth_admin`, `supabase_functions_admin`, `supabase_storage_admin` (and `postgres`, `supabase_admin`). Roles with BYPASSRLS besides `postgres`: `service_role`, `supabase_etl_admin`, `supabase_read_only_user`. None of these has an edge to `grp_batch_writer` (it does not exist yet).
