## Round 3 · QA · 03/10/2026

### Blocking findings

1. **The diagnostic's no-personal-data claim is false.** `00_DIAGNOSTIC_pre-8.8.6_backlog_catalog.sql:129-135` returns the literal values of `notes.custom_course` and `flashcards.custom_subject`. Those are user-authored free-text fields and can contain names or other personal data; `LIMIT 100` and a count beside each value do not sanitize them. `profiles.course_level` at `:92-94` is also free text at the database boundary and therefore needs the same privacy treatment unless its live constraint is proved before values are selected. Revise the diagnostic to answer the design questions using non-identifying aggregates; do not run or save the current block 4 output.

2. **Block 7 does not measure the claimed badge-versus-Review discrepancy.** It uses server `CURRENT_DATE` rather than each student's timezone date, omits the shared course, visibility and `question_type <> 'concept_card'` predicates, counts own cards even though `get_my_cards` always admits them, and considers only explicit `removed`/`course_archived` rows rather than the full absence-of-active-enrollment condition. Its result can therefore overstate or understate the real mismatch. Replace it with an exact set comparison that reproduces the live forecast predicate and the Review page's own-or-active-enrollment boundary.

3. **The affected forecast surface and live check are incomplete.** `Dashboard.jsx:398` renders `get_due_forecast_buckets`; the repo definition says it uses the same enrollment-blind predicate as `get_due_forecast`. Round 2 finding 6.5 does not include this Forward Load surface, and SQL blocks 1-2 do not inspect its live body or grants. Add it to the current-state matrix and diagnostic before the point-6 design is treated as complete.

4. **The course-identity diagnostic cannot prove two absence claims on which design stream B depends.** Listing selected columns on four known tables does not establish that there is no student multi-course registry or custom-course entity in the live schema. Add a bounded catalog inventory for course-related public tables/columns plus the relevant keys, foreign keys and constraints (including `study_group_members` status/role/uniqueness if its live model is to be relied on). Until then, findings 5.2-5.4 remain repo evidence, not live facts.

### Non-blocking findings

1. The cited code at `6fc6ceb` independently supports findings 6.1-6.5, 7.2-7.3, 1.1-1.2, 2.5 and 10.2-10.3. Finding 6.5 is true but incomplete because of blocking finding 3. No `src/` file changed between `6fc6ceb` and current HEAD.

2. The OPEN tail of finding 2.5 can be closed from repo code: `App.jsx:118-125` consumes `postAuthRedirect` after authentication, so the stored join route is honoured after login/signup once a user session exists.

3. The status block's recorded HEAD (`e15e00a`) is stale; audit-time HEAD is `0746fce`. The intervening commits change configuration/docs and add this diagnostic, not `src/`, so the code evidence remains valid. Round 2's statement that "No code or SQL was changed" should say no application or production SQL was changed, because the diagnostic SQL itself was added.

4. Finding 5.4 materially shapes, but does not reverse, the agreed points 5/10 direction. `profiles.course_level` is the current active-course/access selector, not an adequate multi-course reporting taxonomy. Design stream B must define a durable course identity for system and custom labels separately from the current-course selector, state whether "custom courses as real groups" means a reporting/UI group or a new database entity, and define how historical/unassigned/legacy-NULL rows appear. The picker must not infer the set of reportable courses from `profiles.course_level` alone.

5. Finding 10.2 narrows the point-10 acceptance wording. There is no current direct-entry offline form; the acceptance criterion should cover every manual/offline finalization path (normal stop, recovery choices and restored `pendingLog`) at the shared `confirmCategory` write boundary, plus database enforcement. Any future direct-entry writer must use the same contract rather than being treated as a current path.

6. **Agreed-decisions check.** The status bullets are substantively consistent with the prior QA positions summarized by Round 1. In particular, finding 6.6 corrects an earlier factual predicate description without changing the agreed outcome that the badge match Review eligibility. Two qualifications must remain explicit: "custom courses as real groups" is a product/reporting direction, not a verified existing schema fact; and the repository contains no earlier QA round (`Last QA-reviewed round` was 0), so the three-party attribution cannot be independently reconstructed from this thread alone. ### G. Brief B, revised C4 card mapping (supersedes the card-progress bullet of Round 13 C4; answers blocking finding 6)
Both measures must resolve to the same course identity before they are shown in the same group. The authoritative mapping for a **card** is, in order: (1) `flashcards.discipline_id`, if set, is the platform course; (2) otherwise the card's `subject_id`, through `subjects.discipline_id`; (3) otherwise `target_course` text that equals a discipline name; (4) otherwise a non-empty `target_course` is a custom group, grouped with the **same normalization key as study time** (F1); (5) otherwise the card is unassigned and is shown as such. Evidence for existing data: all 2,850 flashcards have a `subject_id` and a `target_course` equal to a platform name, so steps 1-3 resolve every card today and steps 4-5 are empty for flashcards (RUN 5A); one note has a non-platform `target_course` and three notes use a custom subject (RUN 5A). How many cards have a NULL `flashcards.discipline_id` was not measured; it is added to the follow-up diagnostic as a count (D4 above) and the fallback chain makes the result safe either way.
**Rename rule:** platform course names are identifiers used by `profiles.course_level`, `flashcards.target_course` and the live queue and forecast filters, which compare text for equality (RUN 1B). Renaming a discipline is therefore **not supported in v1** without a coordinated data migration, which is a separate project. Because names do not change, displaying platform names by live join cannot drift, and the two measures cannot split one course across two labels.
**Result:** card progress and study time are still separate, never-summed measures, but both land in the same group because both resolve to `discipline_id` (platform) or the same normalized key (custom); anything that resolves to neither lands in "Unassigned" and is shown.
