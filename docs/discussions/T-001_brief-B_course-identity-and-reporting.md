## 1. Invariants (every other artifact must respect these)
- **B-I1.** A platform course is identified by `disciplines.id` and a platform subject by `subjects.id`. Platform course **names are identifiers** (they are compared as text in the live queue and forecast filters, in `profiles.course_level`, `flashcards.target_course` and other columns, section 6) and are **immutable in v1**: renaming a discipline is prohibited and guarded (section 6). **Identity resolution recognises every `disciplines` row, active or not, and names are unique under the catalogue normalization and rows are never hard-deleted in v1 (6.4)**; any new stored course label that matches a platform name under normalization is written in the exact canonical text (5.3a), because live functions compare it as exact text; deactivation changes only what is offered as a new choice (5.5), never what an existing label or session resolves to.
- **B-I2.** A custom course or subject is stored as a **label** (as typed) and a database-generated **key** (the grouping value). The label is **never truncated** (section 5).
- **B-I3.** A new offline log is always classified (platform, custom, or explicit General). NULL means only "no classification recorded"; reports separate rows by `source` and classification, so NULL never has two meanings in one group (section 4.3).
- **B-I4.** Rows written before the change are never back-filled from the student's mutable current course.
- **B-I5.** Course and subject consistency is enforced by the database: on `study_sessions` by a composite foreign key and CHECKs; on `flashcards` and `notes` by a **guard trigger on write** (not a table CHECK), so legacy rows stay editable (section 6.3).
- **B-I6.** Validation **and canonicalisation** of a profile's course label is a trigger that fires only when `course_level` is inserted or changed, **not** a table CHECK (sections 5.3 and 5.3a). A normalized match to a platform or catalogue name is stored in its exact canonical text, by one function.
- **B-I7.** There is one course catalogue, a single server definition, read by Signup, Profile Settings, the access-request form and the logging picker; each surface applies exactly the projection listed for it in 5.5, and none keeps its own list or order.
- **B-I8.** Card progress and study time must resolve to the same course identity before they are shown in the same group; they are never summed.
- **B-I9.** Professors see totals only; the course and subject breakdown is not exposed to them.
- **B-I10.** Existing totals, `get_study_time_stats` and professor batch reports are unchanged.

The CHECK on `profiles.course_level` lists nine labels (CA, CMA, CS) but ends with `OR length(course_level) > 0`, so any non-empty text passes (RUN 5B). 255 of 262 profiles equal a discipline name, 2 are blank, 5 hold other text (RUN 5A).
2. Signup offers nine labels plus custom text (`Signup.jsx:46-56,267-271`); Profile Settings offers only the three CA courses (`ProfileSettings.jsx:30-34`); the access-request form offers ten (`ContentPreviewWall.jsx:17-28`). CMA and CS labels have no discipline.
3. No student course registry is in use (`profile_courses` holds professor rows only: 3 users, 5 rows), no custom-course entity exists, and no `custom_course` column exists anywhere (RUN 5A, 5B). Custom subjects are almost unused (1 flashcard, 3 notes).
4. The product is single-active-course: switching archives enrollments and the queue and forecast filter by the current course using text equality (RUN 4, RUN 1B).
5. `study_sessions` has no course or subject. About 95% of recorded hours are offline manual (1,003.3 h of 1,051.1 h), of which 431 manual rows have no category (RUN 3). The table is immutable for client roles: `authenticated` holds INSERT and SELECT only, with no UPDATE or DELETE (RUN 3).

7. Progress already has a Subject Mastery table for the current course (`Progress.jsx:582-584`).

## 3. Course identity
- **Platform course and subject:** `disciplines.id`, `subjects.id`. Display by live join (no label snapshot), which is safe because names cannot change (B-I1).
- **Custom course or subject:** no entity exists and almost no data uses it. v1 stores the label and the generated key; promotion to an entity is deferred until there is demand.
- **General:** an explicit classification, not NULL.
- **Legacy:** NULL, only for rows before the change (B-I4).
- The picker never derives its list from `profiles.course_level` alone.

## 4. Logging foundation (point 10)
**4.1 Columns on `study_sessions`** (all nullable; rows before the change keep NULL):
- `classification`: `platform`, `custom` or `general`.
- `discipline_id` and `subject_id` (platform): foreign key `discipline_id` to `disciplines(id)`, and a composite foreign key (`discipline_id`, `subject_id`) to a new unique pair on `subjects`. A NULL `subject_id` is allowed and does not weaken the course requirement.
- `custom_course_label` and a stored generated `custom_course_key`; `custom_subject_label` and a stored generated `custom_subject_key`. The key is computed by the database from the label (lower-cased, internal whitespace collapsed, trimmed), so a client cannot make them disagree. There is no uniqueness constraint (no entity). Grouping is by key; a group's display label is the label of the row with the greatest (`created_at`, `id`) for that key. No accent folding or fuzzy matching in v1; "CFA L1" and "CFA Level 1" stay separate groups, which the picker's suggestions from the student's own earlier labels are meant to prevent.
- Adding a stored generated column rewrites the table; at 1,395 rows this is negligible but it takes a table lock and must be in the SQL plan.
**4.2 Constraints (`NOT VALID`, safe because the table is immutable, RUN 3).**
- `platform`: `discipline_id` required, custom columns forbidden, subject optional.
- `custom`: `custom_course_label` required (length rule, section 5), `discipline_id` and `subject_id` forbidden, custom subject label optional.
- `general`: all of them NULL.
- `source = 'manual'` requires a non-NULL classification.
- `source` in (`study_mode`, `practice_mode`) requires a NULL classification in v1; this may be relaxed later if in-app classification is approved.
**4.3 Report contract.** Rows are separated by `source` and classification:
- **Offline, classified:** manual rows with `platform` (one group per discipline), `custom` (one group per key), or `general`.
- **Offline, unassigned (legacy):** manual rows with a NULL classification. The constraint makes this possible only for rows written before the change.
- **In-app, not classified by course:** `study_mode` and `practice_mode` rows, before and after the change, in v1.
- **All-course totals** add every group once; General is included and is attributed to no course.
**4.4 Write path.** Every manual path (normal stop, recovery log-full or log-less, restored pending log) ends at `confirmCategory`, so one change in that function plus the database constraints covers them. Any future direct-entry writer must use the same contract.
**4.5 Picker (mobile-fast).** A compact "Course" row above the category buttons, preselected, always visible before Save; subject optional and skippable; "General" one tap away. The options and their order are the **picker projection** of the single course catalogue (5.5, table), nothing else: current course first; the other active platform courses; the student's own earlier custom labels; General; "Other…" for new text. CMA and CS catalogue labels appear in the picker only when they are the current course or one of the student's own earlier labels. A platform course, **active or inactive**, maps to its discipline (5.5); a current course that equals no discipline at all is offered as a custom entry with its exact label when it fits the limit (5.1), otherwise as in 5.4. The subject list follows the course: a platform course lists its active subjects; a custom course lists the student's own earlier custom subjects for that key. The last subject used per course is remembered on the device only. No student course registry is created in v1.

## 5. Course label length and validation (one contract)
**5.1 Rule.** A course label is trimmed, contains no control characters, and has a length between 1 and **L** characters. L is the larger of 120 and the longest existing `profiles.course_level` value rounded up to the next multiple of 20, capped at 200. **Follow-up RUN F9 (04/10/2026) shows the longest existing value is 19 characters (261 of 263 profiles are 1 to 60, 2 are blank or NULL, none is over 60, none has leading or trailing whitespace, control characters or repeated internal whitespace), so L = 120 is fixed.** **A label is never truncated.**
**5.2 Same rule everywhere:** the Signup custom-course input, Profile Settings, the access-request course field and `custom_course_label` (and `custom_subject_label`).
**5.3 Profile validation is a trigger, not a CHECK (B-I6).** PostgreSQL enforces a `NOT VALID` CHECK against every new row version, so a table CHECK, even `NOT VALID`, is evaluated on **every** update of a row, so one legacy profile with an over-limit or untrimmed value would become impossible to update for unrelated reasons (for example marking onboarding seen). The validation therefore runs in a trigger that fires on insert and only when `course_level` changes, so legacy values stay untouched and updatable. Real-role test: updating an unrelated column of a legacy over-limit profile succeeds. The same trigger also canonicalises (5.3a).
**5.3a Canonical form on write (B-I1, B-I6).** A normalized match to a platform name must be stored in the **canonical exact text**, because the live queue, forecast and course-change functions compare `target_course = course_level` as exact text (RUN 1B; follow-up F3A). One immutable function, `canonical_course_label(text)`, trims, collapses internal whitespace, lower-cases for comparison, and returns: (a) the **exact stored name** of the matching `disciplines` row (active or not); else (b) the exact catalogue text of a matching CMA or CS label of 5.5; else (c) the trimmed input unchanged (a genuine custom label). The same function is the only place this rule lives and is used by: the `profiles` trigger of 5.3, which **rewrites** `course_level` to the canonical text on insert and whenever it changes (so `ca  final` is stored as `CA Final`; a value is rewritten, not refused, because the student's intent is clear); `submit_access_request` for the `course` field; and the `study_sessions` insert path, where a custom label that matches a **discipline** name is **refused** (the client must send the platform classification) and a custom label that matches a catalogue label is stored in its canonical text. The profile trigger is a BEFORE trigger, so the existing AFTER course-change trigger (`fn_course_change_archive_restore`, F3A) sees the canonical value. Signup and Profile Settings may normalise in the browser for display, but the database is the authority. Tests: exact, case-variant and repeated-whitespace values entered through Signup, Profile Settings, the access form and the picker's "Other" are stored canonically and the student's due counts and enrollments are unchanged; a custom label equal to a discipline name is refused on `study_sessions`; the function is the only copy of the rule (a catalog test).
**5.3b Existing non-canonical values.** The five profile values that RUN 5A found by exact comparison to be non-platform were never tested for a normalized match. A privacy-safe aggregate check (counts only, per column, in the second follow-up diagnostic, run G1) reports, for the eight dependent text columns of 6.4, how many values are exactly canonical, **variants of a canonical name** (the same text under normalization but not exact), blank, or other. **Repair rule if any variant exists:** a separately reviewed data fix rewrites those values to the canonical text, only where the normalized match is exact, with per-column before and after counts, a rollback, and a test that the course-change trigger's archive and restore behaviour is understood for each affected student (a rewrite of `profiles.course_level` fires it). No repair is run before that file is approved. F6 already shows no variant between `target_course` and the subject-derived discipline name on cards and notes that have a subject (0 differences).
**5.4 Existing values.** Every existing value up to L is used **exactly** as stored (the session label and key equal the profile's). Because L is fixed at or above the observed maximum, no existing value should exceed it. If RUN F9 shows any value above 200, the following **persistent alias rule** applies to those individual students; no distinct existing values are ever merged by truncation:
- The over-limit profile value is **never offered as a label** and the profile is never changed by the logging flow.
- The first time such a student logs, the picker asks them to type a short alias (up to L characters, their own text). The session stores the alias as `custom_course_label` with its generated key; that group's identity is the alias, by the student's explicit choice.
- **Remembering it, explicit reconfirmation.** No registry and no link between the alias and the profile value is stored. On later logs the earlier alias simply appears as an ordinary `prior_custom` label (5.5); the most recently used custom label is preselected so confirming is one tap, and it is **not** described as "your course". A student whose last custom log was a different course must pick the alias again; that trade-off is accepted for v1. If the student has no custom session yet, the picker asks for an alias.
**5.5 One course catalogue, and the projection each surface applies (B-I7).** There is **one data source**: a single server definition, the **course catalogue**, and every surface reads it. It has three layers:
1. **Platform courses:** every `disciplines` row, in a defined platform order (kind `platform`, carrying `discipline_id` and an `is_active` flag). The catalogue carries **two roles that must not be confused**: *identity resolution* uses all rows, active or inactive, so a label that equals any discipline name always resolves to that `discipline_id`; *selectable alternatives* use only active rows.
2. **Catalogue labels:** the allowed non-platform labels from one shared definition: the nine labels of the profile CHECK are CA Foundation, CA Intermediate and CA Final (these are the platform names), CMA Foundation, CMA Intermediate and CMA Final, and CS Foundation, CS Executive and CS Professional (VERIFIED: `profiles_course_level_check`, RUN 5B; `Signup.jsx:46-56`). The six CMA and CS labels are the non-platform catalogue entries (kind `catalogue`).
3. **Caller overlays**, added by the same function for the signed-in student only: their **current course** (kind `current`) and their **own earlier custom labels** (kind `prior_custom`, never other students' text).
**Normalization and de-duplication (one rule for all surfaces).** Labels are compared after the key normalization of 4.1. A label that appears under more than one kind is shown once, with precedence `platform` over `current` over `catalogue` over `prior_custom`, and keeps the flags of every kind it matched; a label whose normalized text equals the name of **any** discipline, active or inactive, is that platform course and is never stored as a custom label. Precedence decides only the single displayed label and its kind flags; **position is always given by the surface's Order column below** (for example, a current course that equals a catalogue label sits at that label's catalogue position on Signup, Profile Settings and the access form, and first in the logging picker).
**Projections** (a surface applies exactly its row; none keeps its own list; order is within the listed groups):
| Surface | Included | Order |
|---|---|---|
| Signup (no profile yet, no overlays) | active platform courses; catalogue; "Other, type your own" | platform order, then the six CMA and CS labels in catalogue order, then Other |
| Profile Settings | active platform courses; catalogue; the student's current value if not already listed (see rules below); "Other" | active platform, catalogue, then the current value marked "current" if it is outside both, then Other |
| Access-request form | same list as Profile Settings, **preselected** to the current course, subject to the rules below | same as Profile Settings |
| **Logging picker** | `current` (including an inactive platform course, which keeps its `discipline_id`); **active** platform courses other than the current one; `prior_custom` labels (most recently used first, at most ten, "Other" reaches the rest); General; "Other…". **Catalogue labels are excluded** unless they are the current course or a prior custom label. | current, other platform, prior custom, General, Other |
**Rules for the student's current value** (apply on Profile Settings and the access form; the picker follows 4.5):
- *Inactive platform course.* If the current value equals a deactivated discipline, it **stays the student's current course and keeps its identity**: it is shown as current, marked "no longer offered", is never turned into a custom label, and new logs in the picker keep that `discipline_id` (so card progress and study time stay in one group, B-I8). It is **not offered to anyone else** as a choice. Profile Settings invites the student to pick an active course; until they do, nothing breaks. Whether deactivation should also force a course change is outside this brief (decision E9).
- *Over-limit value.* If the current value is longer than L (5.1), it is **not listed as an option**; Profile Settings shows a notice ("Your saved course is too long to use as a name. Choose a course or type a shorter one.") and the access form leaves the course field empty with the same prompt. The profile value is not changed until the student saves a new one (5.4).
The picker is therefore a defined filter of the same catalogue, not a second list. Label length and validation (5.1 to 5.3) apply wherever text is typed.

## 6. Card and note mapping, and the rename prohibition
**6.1 Canonical course for a card or note** is the discipline implied by its subject (`subject_id` to `subjects.discipline_id`); `discipline_id` and `target_course` are copies that must agree with it. Mapping chain for reporting: (1) the subject-derived discipline; (2) if there is no subject-derived discipline but `discipline_id` is set, that discipline; (3) **legacy rows only:** `target_course` text equal to a discipline name; (4) a non-empty other `target_course` is a custom group using the study-time grouping key; (5) otherwise unassigned.
**6.2 Conflicts.** Where `discipline_id` disagrees with the subject-derived discipline, or `target_course` differs from the resolved discipline's name, the row is reported under **"Unassigned (conflict)"** until reconciled. There is no silent preference. Reconciliation is a separate data-fix task with its own SQL and rollback. **Follow-up RUN F6 (04/10/2026) measured it: 0 conflicts.** Every one of the 2,850 flashcards has a subject whose discipline name equals its `target_course`; 125 of 128 notes have a subject and match in all 125; 3 notes have no subject and no discipline (unassigned). `discipline_id` is **NULL on all 2,850 flashcards and all 128 notes**, so it is an unused column today and the mapping chain of 6.1 resolves through the subject for 100% of cards and 125 of 128 notes. The conflict group is therefore empty at present and exists only as a safeguard.
**6.3 New platform cards and notes.** `discipline_id` is required and (`discipline_id`, `subject_id`) is consistent, enforced by a **guard trigger on insert and on update of those columns** (and the same composite foreign key, `NOT VALID`; foreign-key checks are skipped when the key columns are unchanged, to be confirmed by a real-role test). A table CHECK is not used, because it would block edits to legacy rows that lack `discipline_id` (6.2 and B-I5). `target_course` becomes a derived label for new platform rows, set from the discipline by the guard trigger or the creating function (implementation choice). A new platform row never depends on text equality for its identity.
**6.4 Rename prohibition (B-I1).** Platform course names are identifiers used as text in at least these eight columns (RUN 5B): `profiles.course_level`, `flashcards.target_course`, `notes.target_course`, `flashcard_decks.target_course`, `my_cards_enrollment.archived_course`, `study_groups.batch_course`, `study_groups.linked_course`, `access_requests.course`; and in the live queue, forecast and bucket functions, which compare `f.target_course = course_level` as text (RUN 1B). A rename without a coordinated migration would create conflicts and change which cards are due. Therefore **a discipline rename is prohibited in v1**, enforced by a trigger on `disciplines` that rejects any change to `name`; deactivation (`is_active`) is allowed and does not change identity: an inactive discipline still resolves, still owns its cards, notes and sessions, and still appears as a Progress group when it has data (5.5, 7). A rename becomes a separate migration project that updates all dependent columns in one transaction.
**Catalogue write guards (B-I1).** Live evidence (RUN 5B) shows `disciplines` has only its primary-key index: `name` is not unique, so nothing today stops a second row with the same name, or a delete. Identity by name therefore needs three guards, all on `disciplines`: (a) **uniqueness under the catalogue normalization**: a unique index on the normalized name, using the one immutable normalization function that 5.5 and 4.1 also use (trim, collapse internal whitespace, lower-case), over **all rows including inactive ones**, so one label can never resolve to two ids; the three existing rows are distinct (CA Final, CA Foundation, CA Intermediate, RUN 5A), so creation will not fail; (b) **no hard delete in v1**: a trigger rejects DELETE on `disciplines` (deactivate with `is_active` instead), because deleting a row would make an existing profile label, card or session stop resolving to a platform identity and recreate the platform-to-custom split; (c) the rename trigger above. A catalogue label of 5.5 that equals a platform name under the same normalization is the platform course and can never be inserted as a separate entry. Open and not assumed: whether a subject delete is guarded (the new composite foreign key from `study_sessions` restricts deleting a referenced subject; whether `flashcards.subject_id` and `notes.subject_id` have a restricting foreign key is not measured) and the effective write privileges of client roles on `disciplines` and `subjects` (RUN F1 does not list them); the triggers hold regardless of privileges, but TRUNCATE bypasses row triggers, so the tests also confirm that no client role can TRUNCATE.
Acceptance tests: an attempted rename fails; a duplicate-name INSERT fails for an exact duplicate and for variants that differ only in case or whitespace, including against an inactive row; a DELETE fails and deactivation succeeds; a client role cannot TRUNCATE; a catalog test lists the dependent columns and fails if a new one appears unlisted.

## 7. Reporting and Progress by course (point 5)
- Heatmap tooltip stays concise (in-app, offline and total time; point 7); the course and subject appear in a day-detail view for the student only.
- Progress groups: the current course first and expanded; other platform courses, **active or inactive when they have data**, collapsed with one summary line; each custom group by key; **General** as its own group, counted in the all-course totals and attributed to no course; **Unassigned / legacy** (offline, NULL), **In-app, not classified by course** (section 4.3) and **Unassigned (conflict)** (6.2) shown separately; nothing hidden. Headline totals state their scope ("All courses").
- Two measures, never summed (B-I8): card progress (reviews mapped through section 6) and study time (classified sessions). Both resolve to the same identity: `discipline_id` for a platform course, the same grouping key for a custom one.
- Collapse state is remembered in the browser only.
- Professors: totals only (B-I9). Existing totals, `get_study_time_stats` and professor batch reports are unchanged (B-I10); the new groups are an addition, and the all-course totals must reconcile with the existing totals in the real-role tests (section 8).

## 9. Decisions for the Founder (none requested until QA has audited this file)
- **E1.** The picker is the defined projection of the single catalogue (5.5): current course first, other active platform courses, the student's own earlier custom labels, General, Other; CMA and CS catalogue labels appear only when current or previously used; no student registry in v1. Recommend yes.
- **E2.** CMA and CS students use custom text in v1; adding CMA and CS disciplines is a separate catalogue decision. Recommend yes.
- **E3.** One course catalogue (active platform courses plus the six CMA and CS labels, defined once) read by Signup, Profile Settings, the access form and the picker, with the per-surface projections of 5.5 (the picker excludes catalogue labels the student has not used). Needs a Founder choice.
- **E4.** In-app sessions are not classified in v1; reports are separated by source. Recommend yes.
- **E5.** Platform names by live join (safe because renames are prohibited); custom text stored as label plus generated key. Recommend yes.
- **E6.** Professors see totals only. Recommend confirm.
- **E7 (revised).** The label limit is fixed at 120 (follow-up RUN F9: longest existing value 19 characters); labels are never truncated; outliers use a student-confirmed alias, reconfirmed on later logs (one tap only when the most recently used custom label is the alias, otherwise the student picks it again, 5.4). Recommend yes.
- **E8 (revised).** Discipline renames and hard deletes are prohibited in v1 and guarded, and discipline names are unique under the catalogue normalization (deactivate instead of delete). Recommend yes.
- **E9.** A student whose current course is a deactivated discipline keeps it as their current course with the same identity, marked "no longer offered", until they choose another; it is not offered to others. Recommend yes.
- **E10 (new).** `discipline_id` is empty on all existing cards and notes and the subject already determines the discipline for 100% of cards and 125 of 128 notes. Keep deriving the course from the subject at read time in v1 and require `discipline_id` only on new platform rows (6.3), with no backfill of existing rows; a backfill stays an optional separate reviewed fix. Recommend yes.
